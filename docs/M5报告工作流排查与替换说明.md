# M5 报告助手与报告生成：排查及替换说明

检查日期：2026-10-18（北京时间）。依据为当前项目后端代码、用户提供的业务契约，以及仅含合成资料的真实 Dify API 调用。

后续状态更新：用户提供新应用 Key 后，已完成配置、重启和真实页面业务流程验证。
三类任务与六类报告接口均通过；详见 [M5悬浮窗真实联调验收](M5悬浮窗真实联调验收-2026-10-18.md)。
以下旧发布应用失败与“尚未验证”的记录保留为更换 Key 前的排查历史。

## 检查结论

当前配置已启用 `M5_AI_MODE=DIFY`，日报助手和报告生成应用的 Key 都已配置。
实际调用中，开始、入参解析和模型节点成功，已发布应用的 `validate` 节点多次报
`JSONDecodeError: Expecting value: line 1 column 1`，最终工作流失败。
模型输出以 `<think>` 开头；同一批实际返回内容在新版本地代码节点回放均通过。
查询在首轮调用曾成功，随后复测也失败，因此不能按“一次查询成功”认定应用稳定。

这不是“所有报告业务都失效”：报告 AI 失败时后端仍保留确定性指标和事实文本；
日报助手失败时保留原草稿，可手工填写。聊天中的客户查询由后端计算，
“生成报告”聊天指令只准备报告中心的生成条件，这些也不依赖模型生成正文。

需要同时修正的契约问题：

| 位置 | 旧文件问题 | 当前业务要求 / 新版处理 |
|---|---|---|
| 日报提示词 | 允许 PSYCH、COMPLAINT 和沿用专项事件编号 | 普通日报只允许 CUSTOMER / DELIVERY / ENROLLMENT / LEAVE / OTHER，source_event_id 必须 null |
| 日报输出校验 | 仅检查 JSON 和一个文本字段 | 按 DailyContent 字段、长度、数量、类型和后端提供的学生 ID 范围校验；缺字段由代码重算 |
| 报告输出校验 | 只有 answer 也可能通过 | 必须有非空 narrative；只输出 narrative，丢弃模型返回的 metrics、confirmed 等额外字段 |
| 数字与数据说明 | 依赖提示词保留 | 用代码原样附上后端时间、范围、指标值、单位、统计口径和 warnings；null 不变成零 |
| 已发布版本 | 实际输出带思考标签时解析失败 | 处理完整思考标签与 JSON 代码围栏；非法、截断或不符合业务契约的输出仍失败降级 |

仓库旧文件已含去除思考标签的代码，但线上仍报上述错误，提示已发布版本可能未同步，或线上节点配置不同。
仅改本地 YML 不会自动更新 Dify 已发布应用。

## 两份替换文件

| 应用 | 文件 | 后端配置 |
|---|---|---|
| M5_报告助手 | `dify/m5_report_assistant.yml` | `M5_DIFY_ASSISTANT_KEY` |
| M5_报告生成 | `dify/m5_report_generation.yml` | `M5_DIFY_REPORT_KEY`（未配置时兼容回退 `DIFY_REPORT_KEY`） |

分别使用两个 Workflow 应用，不能用企业助手 Key 替代。两份均为：

`Start(payload_json) → prepare → llm → validate → End(output_json)`

输入和输出都是**字符串 JSON**；后端使用 `/v1/workflows/run` 的 streaming 模式，
只有 `workflow_finished` 且 `status=succeeded`、最终契约有效才算成功。
工作流内没有 HTTP 写接口、登录 JWT、数据库连接或自动提交路径。

保留仓库现有 DSL `0.5.0` 和 DeepSeek 插件依赖，默认模型 `deepseek-chat`。
导入目标实例的兼容性与该插件是否可安装仍需在 Dify 控制台确认。
两份工作流只使用后端授权过的数据，不需要知识库；不要把客户明细、心理记录或投诉原文额外加入知识库。

## 导入、发布与接入

1. 在 Dify 导出当前两个应用作备份，再分别导入这两份 YML 为 Workflow。确认输入是 `payload_json`，最终输出是 `output_json`。
2. 打开 LLM 节点，确认 DeepSeek 插件、模型与凭据可用。若实例使用其他供应商，可在界面换成可用聊天模型，保留提示词及两个代码节点。若模型提供 JSON 输出模式可启用，但不能删除业务校验节点。
3. 分别试运行下面的合成样例，确认最后 `output_json` 可以解析，且日报包含 `answer/content`、报告包含 `narrative`。两份应用都要点**发布**，仅保存草稿不更新 API 所用版本。
4. 使用各自应用的 API Key 配置 `backend/.env`。没有更换应用时核对现有 Key；新建应用后换成新 Key。Key 不写入 YML 或前端。

```dotenv
M5_AI_MODE=DIFY
M5_DIFY_BASE_URL=http://YOUR_DIFY_HOST/v1
M5_DIFY_ASSISTANT_KEY=app-REPLACE_WITH_ASSISTANT_KEY
M5_DIFY_REPORT_KEY=app-REPLACE_WITH_REPORT_KEY
# 如已有兼容配置，建议也填同一个报告生成 Key：
DIFY_REPORT_KEY=app-REPLACE_WITH_REPORT_KEY
M5_AI_TIMEOUT=45
```

5. 修改配置后重启后端（路由创建时读取 M5 配置），再从项目根目录执行真实复测：

```bat
backend\.venv\Scripts\python.exe tools\probe_m5_dify.py --live
```

预期 `DAILY_COLLECT=PASS`、`QUERY=PASS`、`REPORT_GENERATE=PASS`。
该脚本只发送合成资料，不保存日报、报告或提交审核；Dify 会正常记录运行并产生模型用量。
需要排查节点时加 `--trace`，仅打印节点状态、字段名称和脱敏错误，不打印模型正文或 Key。
`--replay-local` 是把线上模型输出交给本地新 DSL 校验，**不代表新 DSL 已经发布成功**。

6. 页面验证：员工连续输入今日工作 → “没有困难” → 明日计划，确认原有工作不丢失；打开“我的日报”人工核对后提交。
主管通过报告中心选择时间与员工范围，检查预览指标、正文、warnings，并用该次 `snapshot_id` 保存。
分别覆盖六类报告及各自权限，确认数据不足时保留提示、生成失败时保留表单与事实文本。

导入流程及版本兼容检查参考 [Dify 官方应用管理文档](https://docs.dify.ai/en/cloud/use-dify/workspace/app-management)。

## 合成试运行样例

将下面 JSON 原文粘贴到 Start 的 `payload_json` 文本框，不要再在外面包 `inputs`。

日报收集：

```json
{
  "task": "DAILY_COLLECT",
  "message": "今天整理公开活动资料2次，没有困难。",
  "draft": {},
  "history": [],
  "selected_student_ids": [],
  "report_date": "2026-10-18",
  "content_policy": "日报仅普通工作，禁止心理原文、投诉明细和专项事件引用"
}
```

多轮时由后端把上次 `content` 作为本次 `draft` 传入；本次 `message` 可填“明天继续整理活动资料”。
没有明确工作量时允许 `items=[]`，不能替用户猜测次数；未提供困难时保持空值并追问，“无困难”才填“无”。

报告生成：

```json
{
  "task": "REPORT_GENERATE",
  "type": "DAILY_DAY",
  "start_date": "2026-10-18",
  "end_date": "2026-10-18",
  "scope": "本人 · 合成验收部门",
  "metrics": [
    {"key": "approved_daily", "label": "已通过有效日报", "value": 0, "unit": "篇", "formula": "只统计审核通过版本", "available": true},
    {"key": "daily_coverage", "label": "审核通过覆盖率", "value": null, "unit": "%", "formula": "分母为零时无值", "available": true}
  ],
  "facts": [{"section": "工作记录", "text": "当前范围无已审核日报，不推断已完成工作。"}],
  "warnings": ["合成验收资料；当前范围没有已通过日报"]
}
```

还支持 `CUSTOMER_OPERATION / DAILY_WEEK / PSYCH_WEEK / COMPLAINT_WEEK / MANAGER_WEEK`。
实际指标和事实必须继续由后端生成，不应把这些合成数据放进正式业务表。
