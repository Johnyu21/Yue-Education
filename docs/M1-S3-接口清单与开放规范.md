## 二、设计说明

### 2.1 为什么接口文档要"以代码为准"

**问题**：手写 doc 和代码**会不一致** —— 改了代码忘了改文档，
队友照着旧文档写，对不上。

**所以**：**代码是唯一真相**，FastAPI 自动生成 OpenAPI：

```bash
# 起服务后直接取
curl http://localhost:8000/openapi.json

# 或打开可视化文档（Swagger UI）
open http://localhost:8000/docs
```

**Swagger UI 是最实用的** —— 浏览器里能看、能点、能试。

**本文档的角色**：只写**代码里看不出的东西**（谁负责、哪些没做、白名单规则）。

### 2.2 为什么要有 DTO 白名单

**问题（提权漏洞）**：如果后端图省事直接 `data → model`：

```json
// 客户端想偷偷提权，多传了字段
POST /api/v1/employees/leads
{ "name":"张三", "mobile":"138...", "owner_user_id": 999, "dept_id": 1 }
                                        ↑ 把线索改到别人名下
```

**所以**：**写入接口只接受白名单字段，未声明的一律拒绝**。

**权限相关字段永不接受客户端传入**：
`owner_user_id` / `dept_id` / `employee_role` / `user_id` /
`can_handle_feedback` / `psych_access_enabled` / `priority` / `assignee_user_id`

**这些一律由后端按登录身份和业务规则决定。**

### 2.3 为什么"范围外返回 404 不是 403"

403 会说"这条数据**存在**，你没权限" → **泄露存在性**。
404 什么都推断不出 → 攻击者无法探测哪些 id 有效。

**做法**：用 `scope.get_or_404(db, Model, id)`（M1-05 已实现）。

### 2.4 为什么有"空壳"接口（501）

**问题**：五个人并行开发，**没做完的接口**如果不存在，
前端调会得到 404，**分不清"没做"还是"路径写错了"**。

**所以**：**接口先都注册好**，未实现的返回：
```json
{"code":"NOT_IMPLEMENTED","message":"API032 尚未实现（负责人：M3）"}
HTTP 501
```

**好处**：前端知道**接口存在、只是没做完**；也一眼看出**归谁做**。

## 五、使用方式

### 5.1 取真实接口定义（推荐）

```bash
# 启动后端
cd backend && source .venv/bin/activate
uvicorn app.main:app --reload --port 8000

# 方式一：浏览器看（Swagger UI，能点能试）
open http://localhost:8000/docs

# 方式二：取机器可读的 OpenAPI
curl http://localhost:8000/openapi.json > openapi.json
```

### 5.2 前端 / Dify 怎么对接

- **前端**：从 OpenAPI 生成 TypeScript 类型（如 `openapi-typescript`），**别手写**
- **Dify**：工具调用的路径、参数，**照 OpenAPI 填**

### 5.4 DTO 白名单怎么写

```python
from pydantic import BaseModel

# ✅ 只声明允许客户端传入的字段
class LeadCreate(BaseModel):
    name: str
    mobile: str
    city: str | None = None
    # ⚠️ 不写 owner_user_id / dept_id —— 客户端传了也接收不到

# Pydantic 默认忽略未声明字段；
# 如需"严格拒绝"（发现多传就报错）：
class LeadCreate(BaseModel):
    model_config = {"extra": "forbid"}   # ← 多传字段直接 422
    ...
```

## 六、API 变更流程（M1 职责）

```
① 想改接口（加字段 / 改路径 / 改权限）
   ↓
② 开一个分支 + PR，在 PR 里写清：
   - 影响的字段
   - 影响的 API 编号
   - 谁在调用（前端 / Dify）
   - 配套的测试
   ↓
③ 评审：
   - M1 审 SQL / 公共文件变更
   - 模块负责人审业务规则
   - M5 确认前端类型
   ↓
④ 合并进 main
```

**依据**：M1 文档「交接与合并约定」——
"变更单须写影响的字段、API 编号、调用方与测试"。

## 七、注意事项

| ❌ 不要 | 为什么 | ✅ 应该 |
|---|---|---|
| 手写一份接口 doc 然后维护 | 和代码不一致 | **以 OpenAPI 为准**，doc 只写补充 |
| 直接 `data → model` 存库 | **提权漏洞**（客户端能改 owner） | 用 DTO 白名单 |
| 范围外返回 403 | 泄露"数据存在" | 用 `scope.get_or_404` → 404 |
| 改接口不通知调用方 | 前端/Dify 会挂 | 走变更流程 + PR |
| 把未实现的接口藏起来 | 前端分不清"没做"和"路径错" | 保留空壳（501 + 负责人） |
| 手动改 `openapi.json` | 下次启动就被覆盖 | 改代码，重启自动生成 |

### ⚠️ 两条硬规矩

1. **接口的"真相"永远是代码** —— `04_API接口文档.md` 是设计稿，
   **实现后有偏差以代码为准**（用 OpenAPI 取）。

2. **改公共接口（如统一响应格式）要先过 M1** ——
   它影响所有模块，一个人改了全组遭殃。
