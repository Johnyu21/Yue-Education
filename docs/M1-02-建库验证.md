## 二、负例验证（插错数据必须失败）

**这是 M1-02 的核心验收标准**——**约束必须真的拦得住**。

| # | 场景 | 预期 | 实际结果 |
|---|---|---|---|
| 1 | 插不存在的部门 id（`dept_id=999`） | 失败 | ✅ `violates foreign key constraint sys_user_dept_id_fkey` |
| 2 | **学生却带员工角色**（`STUDENT` + `ADVISOR`） | 失败 | ✅ `violates check constraint sys_user_check` |
| 3 | **非法枚举值**（`user_type='TEACHER'`） | 失败 | ✅ `violates check constraint sys_user_check` |
| 4 | **部门把自己当上级**（`parent_id=自己`） | 失败 | ✅ `violates check constraint sys_department_check` |
| 5 | **重复手机号** | 失败 | ✅ `duplicate key ... crm_lead_mobile_key` |
| 6 | **状态改 SIGNED 却不填 `signed_at`** | 失败 | ✅ `violates check constraint crm_lead_check` |
| 7 | **状态改 LOST 却不填流失原因** | 失败 | ✅ `violates check constraint crm_lead_check1` |
| 8 | **请假结束早于开始** | 失败 | ✅ `violates check constraint student_admin_service_check` |
| 9 | 正确的变更（SIGNED + `signed_at`） | **成功** | ✅ `UPDATE 1` |
| 10 | 正确的请假（结束晚于开始） | **成功** | ✅ `INSERT 0 1` |

**结论：数据库约束全部真实生效**——不是写了没用。

## 三、⚠️ 必填字段清单（M2-M4 写代码前必看）

**验证时踩到的坑**：`schema.sql` 里有些字段**没写注释但其实是 `NOT NULL`**。
如果不知道，写代码时**插入会直接失败**。

### 3.1 三个"隐形的必填字段"

| 表 | 字段 | 为什么必须填 |
|---|---|---|
| `crm_lead` | **`request_key`** (UUID) | 幂等键，防重复提交 |
| `student_admin_service` | **`request_key`** (UUID) | 同上 |
| `student_admin_service` | **`dept_id`** | 申请要记"属于哪个部门" |
| `student_admin_service` | **`assignee_user_id`** | **处理人必填**——请假必须指派给具体的人 |
| `event_registration` | **`request_key`** (UUID) | 幂等键 |
| `student_application_progress` | **`request_key`** (UUID) | 幂等键 |

**`request_key` 是什么**：一个**随机 UUID**，每次提交带一个。
**作用**：防止"网络重试导致同一条数据插两次"。
写代码时**每次请求生成一个 `gen_random_uuid()`**。

### 3.2 写法示例（正确插入一条线索）

```python
# ❌ 错的（会失败，缺 request_key）
INSERT INTO crm_lead(name, mobile, source, dept_id)
VALUES ('张三', '138...', 'WEBSITE', 1)

# ✅ 对的
INSERT INTO crm_lead(name, mobile, source, dept_id, request_key)
VALUES ('张三', '138...', 'WEBSITE', 1, gen_random_uuid())
```

### 3.3 必填字段总表（按表）

| 表 | 必填（除 id/时间戳外） |
|---|---|
| `sys_user` | `username`、`password_hash`、`real_name`、`user_type` |
| `sys_department` | `code`、`name` |
| `sys_class` | `name`、`dept_id` |
| `crm_lead` | `mobile`、`source`、`dept_id`、**`request_key`** |
| `crm_follow_up` | `lead_id`、`actor_user_id`、`follow_up_type`、`content` |
| `employee_daily_report` | `employee_user_id`、`report_date`、`original_text`、`dept_id` |
| `student_profile` | `user_id`、`dept_id` |
| `student_admin_service` | `student_profile_id`、**`dept_id`**、`service_type`、`title`、`description`、`submitted_by_user_id`、**`assignee_user_id`**、**`request_key`** |
| `student_feedback_ticket` | `student_profile_id`、`category`、`subject`、`content` |
| `student_psych_profile` | `student_profile_id`、`version_no`、`assessment_date`、`business_timezone`、`observed_at`、`source_event_key`、`assessment_source`、`emotion_state`、`assessment_data`、**`consent_at`** |
| `student_application_progress` | `case_no`、`student_profile_id`、`sequence_no`、`item_type`、`title`、`stage`、`assignee_user_id`、`recorded_by_user_id`、`occurred_at`、`request_key` |
| `event_lecture` | `title`、`organizer_user_id`、`description`、`start_at`、`end_at`、`signup_deadline`、`capacity` |
| `event_registration` | `event_id`、`registrant_name`、`mobile`、`request_key` |
| `notification` | `recipient_user_id`、`category`、`title`、`content`、`business_event_key` |

> ⚠️ **`student_psych_profile.consent_at` 也必填**——**没有授权时间就存不了心理数据**。
> 这是合规设计：**先取同意，再记录**。

## 四、如何复现这次验证

**任何人想自己验一遍，照这三步**：

```bash
# 1. 起一个空库
docker run --name m102 -e POSTGRES_PASSWORD=t -e POSTGRES_DB=education -d postgres:16

# 2. 执行 schema.sql（-v ON_ERROR_STOP=1 保证出错就停）
docker exec -i m102 psql -U postgres -d education -h 127.0.0.1 \
  -v ON_ERROR_STOP=1 < schema.sql

# 3. 数表（应输出 19）
docker exec m102 psql -U postgres -d education -h 127.0.0.1 -t \
  -c "SELECT count(*) FROM information_schema.tables WHERE table_schema='public';"
```

  VALUES ('s1','h','学生','STUDENT','ADVISOR');"
