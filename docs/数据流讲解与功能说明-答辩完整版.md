# 第一部分 · 数据流白话讲解（口头答辩用）

> 本文用最通俗的话，讲清楚每一条数据的「从哪来 → 经过什么 → 到哪去」。目标是你能照着这段话，向评委用口头把系统讲明白。

---

## 开场：一句话概括这个系统

这个系统就是一个留学服务平台的"中枢"。访客来了变成客户，客户签约变成学生，学生在读期间通过助手办理请假、投诉、查成绩这些事，顾问和班主任通过助手去服务这些学生，最后系统把所有人干的事汇总成日报和周报给管理层看。

数据的大方向就一句话：**人从"访客"变成"客户"再变成"学生"，事从"学生提出来"流到"老师处理"再"通知回学生"，最后所有事沉淀成"报告"。**

## 主线一：访客 → 客户 → 学生（获客转化链）

### 1. 访客留资（这个人是怎么被记下来的）

**从哪来**：访客在官网首页填一张留资表单，或者在右下角的客服对话框里说"我想了解德国留学"。

**经过什么**：后端收到后，先拿手机号查一遍——这个人以前有没有留过联系方式。
- 没来过 → 新建一条客户档案，记下姓名、手机号、来源渠道。
- 来过 → 不重复建，只在原来的档案上补上这次新填的信息（比如这次补充了意向国家）。
- 接着看"他有没有选意向项目"：选了德国项目，就自动分到德国项目对应的部门；没选，就先放进一个"公共待认领池"。

**到哪去**：数据落进「客户表」和「跟进记录表」，回执只告诉访客"已收到"，不暴露内部信息。待认领池里的客户，**所有顾问都能看到，谁先认领就归谁负责**。

一句话：**访客说的话 → 查重去重 → 变成一条客户记录 → 按项目分部门或进公共池 → 顾问认领。**

### 2. 客户研判（简历怎么变成"符不符合"）

**从哪来**：顾问拿到一份客户的简历（PDF / Word / Excel / 文字都行），上传发起研判。

**经过什么**：
1. 后端先把简历文字提取出来，发给 AI（Dify）。
2. AI 只做一件事：从简历里**原样找出** 16 个字段（姓名、年龄、学历、意向国家、家庭经济、犯罪记录等），并标明每个字段是从简历第几行抄出来的（证据）。
3. AI **不做判断**——它不负责说"这个人合不合格"。
4. 顾问核对 AI 抽的对不对，确认后，后端再用已经审核好的规则（比如"德国项目要 18 到 35 岁、高中以上学历"）去算：符合 / 不符合 / 信息不够。

**到哪去**：结论（符合/不符合/待补充）和分数写回客户档案，简历的提取证据也一起存档。

一句话：**简历 → AI 抽字段（带原文证据）→ 顾问核对 → 后端规则判定 → 结论存回客户档案。** AI 只当"抄写员"，判断权在后端规则。

### 3. 签约转学生（客户怎么变成正式学生）

**从哪来**：顾问确认客户要签约了，点"转学生"。

**经过什么**：后端在**一个事务里同时做 5 件事**（要么全成功，要么全回滚）：
1. 给学生建一个登录账号（生成临时密码）。
2. 建学生档案（记录他的顾问、班级、入学信息）。
3. 关联他报的项目。
4. 把原来那条客户记录改成"已签约"。
5. 记一条"签约"的跟进记录。

**到哪去**：这 5 份数据分别落进账号表、学生档案表、项目关联表、客户表、跟进表。最后通知顾问和主管"转学生成功了"。学生的临时密码**只在这一次返回**，之后系统里再也查不到明文密码。

一句话：**签约 → 一个事务原子地建账号+档案+项目+标记签约+记跟进 → 通知顾问，临时密码只出现一次。**

## 主线二：学生在读期间的服务（学生侧）

### 4. 请假申请（数据从学生流到班主任再流回来）

**从哪来**：学生在学生助手里说"我要请假，10月20到21号"，或者直接在页面填请假表。

**经过什么**：
1. 后端先锁住这条学生记录，检查他这段时间是不是已经有请假在审批中（防止重复请假）。
2. 确定该谁审批：请假、考务 → **班主任**；改资料 → **个人顾问**；其他 → 部门主管。
3. 生成一张"待审批"的申请单，通知审批人。

**到哪去**：申请单落进「行政申请表」，通知发到班主任。班主任点同意/驳回后，状态更新，**再通知回学生**"你的请假已通过/被驳回"。

一句话：**学生提请假 → 锁行查重叠 → 路由到班主任 → 通知班主任 → 审批 → 通知学生。** 这是一个完整闭环。

### 5. 投诉工单（售后怎么闭环）

**从哪来**：学生提交投诉、建议或咨询。

**经过什么**：生成一张工单，状态是"待处理"，通知部门主管（通知里**不含投诉原文**，保护隐私）。有售后权限的员工认领 → 状态变"处理中"→ 跟进、解决，写处理结果 → 状态变"已解决"，**自动通知学生**"你的投诉已解决"→ 学生确认关闭，或者不满意就重开 → 关闭后可以打分评价。

**到哪去**：工单落进「工单表」，状态一路走 `待处理 → 处理中 → 已解决 → 已关闭`，每一步都有通知和时间记录。

一句话：**学生投诉 → 进工单池 → 员工认领处理 → 解决后通知学生 → 学生确认关闭 → 评价。** 全程留痕。

### 6. 心理关怀（怎么发现和跟进风险）

**从哪来**：学生在对话里说话（学生助手），前提是学生已经点了"同意心理关怀"。

**经过什么**：
1. 先做**最直接的一层**：后端用关键词规则扫学生的消息，只要出现"想死""自残"这类词，**立刻**记一条高危预警——这一步不等 AI，AI 挂了也不漏。
2. 第二层：AI 顺便判断一下情绪（正常/低落/很负面），作为补充观测。
3. 根据最近几天的情绪走势，用规则判断要不要升级预警。

**到哪去**：情绪观测落进「心理观测表」（一条条版本化记录），预警落进「预警表」，通知**班主任 → 顾问 → 主管**（通知里不写心理原话）。老师介入后，预警走"待复核 → 确认 → 处理中 → 关闭"。

一句话：**学生说话 → 直接词先秒级告警（不依赖AI）→ AI 补情绪观测 → 规则判断 → 通知班主任/顾问/主管 → 人工跟进关闭。** 权限上只有授权的人能看。

### 7. 成绩 / 日程 / 申请进度（学生只读，员工录入）

**从哪来**：成绩和日程由**授权的老师**录入（来源标"人工录入"），留学申请进度由顾问往里追加事件（比如"文书已完成""签证已递交"）。

**经过什么**：学生查的时候，后端只返回**他自己**的数据，生产环境还会过滤掉演示用的测试数据。

**到哪去**：成绩存「成绩表」，日程存「日程表」，申请进度存「进度表」（每个事项按序号串成一条时间线）。学生还能给日程设提醒，到点由定时任务发通知。

一句话：**老师录入成绩/日程/进度 → 学生只读本人数据 → 可设提醒，到点通知。** 数据流向是"老师写、学生读"。

### 8. 升学意向（二次转化的机会）

**从哪来**：学生在助手里表达"我想读硕士"。

**经过什么**：助手列出已发布的升学项目，学生选一个，生成确认卡，确认后提交。

**到哪去**：不建新客户，只在原客户上追加一条"升学意向"跟进记录，**通知他的顾问**去跟进。

一句话：**学生表达升学意向 → 选项目 → 确认 → 记一条跟进 → 通知顾问。** 挖掘存量客户的二次价值。

## 主线三：员工 / 顾问的工作（员工侧）

### 9. 客户跟进与认领

**从哪来**：顾问看到待认领池里的客户，或者自己客户的后续互动。

**经过什么**：认领 → 客户归属变成这个顾问；每次沟通、状态变化（跟进中/已流失）、分配转派，都追加一条跟进记录，状态机管着合法流转。

**到哪去**：跟进记录落进「跟进表」（只增不改，像流水账），客户状态同步更新到「客户表」。

一句话：**客户动作 → 追加跟进记录 + 更新客户状态。** 跟进是只增不改的流水，保证可追溯。

### 10. 行政审批（班主任/主管的角色）

班主任收到学生的请假申请，在自己的待办里审批；主管还能审批部门日报、分配处理人、维护项目和活动。这些数据流都是"学生/员工发起 → 路由到有权的人 → 审批 → 通知发起人"的同一套闭环。

### 11. 日报与报告（工作怎么沉淀）

**从哪来**：员工每天口述或填写"今天干了啥"。

**经过什么**：AI 把口述整理成结构化的日报（工作概述、工作明细、困难、明日计划），员工核对后提交，主管审核通过后，这份"通过版"就进入汇总。改日报会产生新版本，报告只引用**已通过的那一版**，不会被未审核的改动影响。

**到哪去**：日报落「日报表」（带版本），报告是后端算好指标、AI 只负责润色文字，最后存成快照，可导出 Word / PDF。

一句话：**员工口述 → AI 整理日报 → 提交 → 主管审核通过 → 进入汇总 → 后端算指标 + AI 润色 → 报告快照 → 导出。**

## 主线四：六个 AI 助手的数据流（进 AI → 出 AI）

先记一个总规律：**所有助手都是"后端把上下文打包给 AI → AI 判断意图并填草稿 → 后端校验 → 需要写库的先生成确认卡，用户点了确认才真正写库"。AI 只负责"理解"和"整理"，绝不直接改数据库，也拿不到登录密码。**

### 12. 客服助手（访客）

访客发一句话 → 后端把这句话 + 已发布项目列表 + 开放活动列表打包 → 发给 AI → AI 判断这是"问问题 / 想留电话 / 想报名活动 / 闲聊 / 越界" → 后端校验后，留资和报名会生成一张确认卡，访客确认了才真正提交。数据流：**访客 → AI 识别意图 → 确认卡 → 落库。**

### 13. 学生助手

学生发话（查成绩、请假、投诉、聊情绪）→ 后端带上"这是本人 + 心理授权状态 + 可选项目"→ AI 识别是"查询"还是"办理"→ 查询类后端直接查本人数据返回；办理类先生成确认卡 → 学生确认 → 走普通业务接口落库。数据流：**学生 → AI 识别 → 本人数据查询 或 确认卡办理。**

### 14. 企业助手（员工）

员工发话（查客户、记跟进、审批请假、处理工单、查日报）→ 后端带上"这个员工的身份和能力范围"→ AI 识别出 21 种意图之一 + 参数 → 后端按权限查询或生成确认卡 → 员工确认后执行。数据流：**员工 → AI 识别意图和参数 → 授权查询 或 确认卡执行。**

### 15. 客户研判（AI 只当抄写员）

顾问传简历 → 后端把简历文字 + 已核对事实 + 审核过的规则发给 AI → AI 从原文抽 16 个字段并标证据行号 → **后端规则引擎判定**（AI 不判定）→ 结论写回客户。数据流：**简历 → AI 抽字段带证据 → 后端判定 → 结论落库。**

### 16. 报告助手（日报）

员工口述"今天整理资料2次，没困难" → 后端把口述 + 已有草稿打包 → AI 整理成结构化日报草稿 → 后端校验格式 → 返回给员工核对。数据流：**口述 → AI 结构化 → 日报草稿。**（这里 AI 是 Chat 模式对话，返回结构化内容）

### 17. 报告生成

员工点"生成报告" → 后端先自己算好所有指标（人数、篇数、趋势）和脱敏事实 → 把这些数字和事实打包给 AI → AI 只负责"把数字串成一段通顺的中文正文" → 后端存快照。数据流：**后端算指标 → AI 润色文字 → 报告正文 → 存快照。** AI 不碰数字，数字全是后端算的。

---

## 结尾：通知和权限是两条贯穿始终的暗线

- **通知**：几乎每个闭环的最后一步都是"通知对方"（学生提交通知老师，老师处理通知学生）。通知按"接收人 + 事件"去重，和业务数据在同一个事务里一起提交，所以不会出现"业务成功了但通知没发出去"。

- **权限**：数据每流到一个环节，后端都重新查一遍"当前这个人有没有权利看/办"。AI 里声称的身份不算数，一律以后端登录身份为准。这就是为什么所有数据流里，AI 只做理解、写库都走确认卡和后端鉴权。

---

**一句话收尾**：这个系统的数据流，本质就是"**人**（访客→客户→学生）在流转，**事**（申请、工单、预警）在闭环，**助手**（AI）只理解和整理，**后端**负责鉴权和落库，最后一切沉淀成**报告**。"

## 一、系统总览

### 1.1 技术栈与分层

| 层 | 技术 | 说明 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite | 单入口，`App.vue` 按 `route.path` 动态渲染，无独立路由表 |
| 后端 | Python / FastAPI | 分层：`controller → service → repository → model` |
| 数据库 | PostgreSQL | 19 张业务表 + 幂等/审计支撑表 |
| AI | Dify 1.12.1（DSL 0.5.0） | 6 个 Workflow，统一 `payload_json` / `output_json` 字符串契约 |
| 模型 | deepseek-v4-flash | 只在 Dify 工作室配置，密钥不进后端代码 |

### 1.2 模块划分

| 模块 | 内容 |
|---|---|
| M1 架构 | 认证、权限、响应、数据库、事务、通知、文件、定时任务 |
| M2 获客研判 | 三渠道获客、客服 Agent、客户研判、活动报名 |
| M3 企业助手 | CRM、转学生、日报、员工待办 |
| M4 学生助手 | 学生页面、行政、售后、心理、教务 |
| M5 智能报告 | 五类报告、前端骨架与集成 |

### 1.3 角色体系

| 角色 | 判定 | 普通业务范围 | 心理/投诉敏感数据 |
|---|---|---|---|
| 访客 | 未登录 | 已发布项目与活动、本次本人提交 | 无 |
| 学生 | `user_type=STUDENT` | 本人档案与业务 | 本人工单学生视图；心理仅授权设置，不回显内部标签 |
| 新员工 | `NEWCOMER` | 员工公开信息、本人日报 | 不默认获得 |
| 顾问 | `ADVISOR` / `SENIOR_ADVISOR` | 本人客户、负责学生、明确指派事项 | 需专项授权 |
| 班主任 | 有 `classTeacherOfIds` 的员工 | 当前本班学生 | 专项授权后在负责范围内 |
| 主管 | `sys_department.head_user_id` | 实际主管部门 | 专项授权 + 部门范围同时满足 |
| 管理员 | `ADMIN` | 全域普通业务 | 仍须专项授权，不因 ADMIN 自动开放 |

> 主管身份只来自 `sys_department.head_user_id`，班主任只来自 `sys_class.head_teacher_id`，不由前端或自然语言声明决定权限。

通用约定：业务 ID 一律以**字符串**对外；时间统一 **TIMESTAMPTZ**（入库 UTC、展示 Asia/Shanghai）；每个可写行都有 `version` 乐观锁字段。

## 三、核心数据流详解

> 每条数据流用「文字流程图」表达数据如何从一端流向另一端，并标注关键代码位置。

### 3.1 访客留资数据流

```
访客提交留资（表单 WEBSITE / 对话 CHAT / 活动 EVENT / 员工 MANUAL）
   │  POST /api/v1/public/leads（公开，限流）
   ▼
lead_service.capture_lead / acquire_lead
   │  ① 幂等预占位：写 public_request（request_key + 指纹，冲突→409）
   │  ② 手机号规范化 + 事务级咨询锁（防并发重复建档）
   │  ③ request_key 复用检查（同键直接返回既有结果）
   │  ④ 手机号去重：命中既有客户 → version+1、只补空事实、不改归属
   │  ⑤ 部门路由：有意向项目 → project.default_dept_id；无项目 → dept_id=NULL（未路由池）
   │  ⑥ 完整度计算：name+mobile+gender/city/education 全有 → COMPLETE，否则 MINIMAL
   ▼
写 crm_lead（status=NEW，source，dept_id，request_key，version=1）
   + crm_follow_up（follow_up_type=ACQUIRED，event_key=uuid5 幂等去重）
   ▼
回执 { accepted:true, receiptNo:request_key }（防匿名探测，不回客户是否存在/ID/姓名/顾问）
```

**后续归属流转**：未路由客户（`dept_id IS NULL`）与未分配客户（`owner_user_id IS NULL`）进入「待分配池」，**所有顾问/主管可见并可抢单认领**（`crm_service.list_leads` 传 `or_unrouted=True`；`_can_view_lead`/`_can_claim_lead` 放行）；认领成功后补 `owner_user_id` 与 `dept_id`。

### 3.2 客户研判数据流

```
顾问提交简历（POST /employees/leads/{id}/assessments）
   ▼
assessment_service.assess_lead
   │  ① 范围校验（越权 404）+ 项目校验
   │  ② 事务内：锁客户行 → 版本比对 → 写 assessment_status=RUNNING、request_id、version+1
   │  ③ 事务外：解析简历文本 → 调 Dify 提取 16 字段（不持有行锁）
   │  ④ 规则引擎本地判定（AI 提取只作参考，不参与判定）
   │     assessment_rules.evaluate_project：all_of/any_of → MATCH / NO_MATCH / NEEDS_INFO
   ▼
事务内条件回写：UPDATE crm_lead SET assessment_report、latest_score、assessed_at
   WHERE assessment_request_id=本次请求（旧任务作废，防覆盖）
   ▼
失败 → 只写 FAILED + 错误码，保留上一份成功报告
```

判定结论只能来自后端确定性规则；模型提取的事实必须经「顾问核对确认」后才进入正式事实。

### 3.3 签约转学生数据流（5 表原子事务）

```
顾问签约（POST /employees/leads/{id}/conversion）
   ▼
crm_service.convert_to_student（@idempotent + with_business_transaction）
   │  ① 锁客户行 + 可见性校验
   │  ② 幂等：已有档案且同 request_key → 返回 already_converted（不再给密码）
   │  ③ 前置校验：状态非 SIGNED、版本、contract_confirmed、项目/班级/班主任/顾问有效、手机号未占用
   ▼
同一事务内写 5 张表：
   ① sys_user（STUDENT 账号，生成 7 天临时密码）
   ② student_profile（converted_lead_id、advisor、dept、class、consent=NOT_GIVEN）
   ③ student_course_enrollment（ENROLLED）
   ④ crm_lead（status=SIGNED、signed_at、contract_ref/amount/currency）
   ⑤ crm_follow_up（follow_up_type=SIGNED）
   ▼
通知：顾问 + 部门主管（正文不含密码）
临时密码只在首次成功响应出现一次（幂等回放时剥离 initial_credentials）
```

### 3.4 学生请假（行政服务）数据流

```
学生提交请假（POST /api/v1/services，来自表单或学生助手确认卡）
   ▼
student_service.submit_service（@idempotent）
   │  ① 取学生档案 + 校验 confirmed
   │  ② 幂等：按 request_key 复用既有结果
   │  ③ AI 确认凭据 verify_confirmation（助手发起时）
   │  ④ 锁学生档案行 → 内容校验 → 请假重叠检查（与 PENDING/APPROVED 的 LEAVE 比时间区间）
   │  ⑤ 定审批人：LEAVE/EXAM→班主任，INFO_CHANGE→个人顾问，OTHER→部门主管
   ▼
写 student_admin_service（status=PENDING、assignee_user_id、handling_history=[]）
   + 通知审批人（SERVICE_SUBMITTED）
   ▼
审批（POST /services/{id}/decision）
   │  权限：本人/管理员/主管部门主管
   │  INFO_CHANGE 且 APPROVE → 旧值比对 + 身份核验 + 改 username 时 token_version+1 撤销旧会话
   ▼
写 status=APPROVED/REJECTED、decision_note、decided_at、version+1
   + 通知学生（SERVICE_DECISION）
```

### 3.5 售后工单数据流（状态机）

```
PENDING → PROCESSING → RESOLVED → CLOSED
                      ↑（重开）  │
```

| 动作 | 接口 | 关键变更 | 通知 |
|---|---|---|---|
| 学生提交 | `POST /me/feedback-tickets` | 写工单 PENDING，COMPLAINT→priority=HIGH | 通知部门主管（不含投诉正文） |
| 员工认领 | `claim` | assignee=本人，status=PROCESSING，记 first_response_at | — |
| 处理/转派/解决 | `handling` | ASSIGN（主管转派）/ NOTE（受理人）/ RESOLVE（写 resolution、is_notified=True） | RESOLVE 通知学生 FEEDBACK_RESOLVED |
| 学生确认关闭 | `confirm` | RESOLVED→CLOSED + closed_at | — |
| 重开 | `reopen` | RESOLVED→PROCESSING，reopened_count+1 | — |
| 评价 | `rating` | 仅 CLOSED，写 satisfaction_rating/comment | — |

> 权限：受理/跟进需 `can_handle_feedback`；主管转派需 `can_handle_feedback` 且主管关系；处理人默认自己（前端不再要求手选他人）。

### 3.6 心理关怀数据流

```
学生授予心理同意（PUT /me/psych-consent → psych_consent_status=GRANTED）
   ▼
学生对话（学生助手 / 表单）
   │  ① 直接风险词检测（想死/自残等）→ 立即落 RULE 观测 + HIGH 预警，不等 Dify
   │  ② Dify 情绪观测（observe_emotion=true 时）→ 落 DIFY 观测
   ▼
写 student_psych_profile（version_no 递增、source_event_key 去重、is_valid）
   ▼
按近 N 日最终有效状态做风险规则评估（H_4N / H_2V / M_MIX / L_1V / L_2N）
   ▼
预警 upsert：无开启预警 → 新建 student_psych_alert（PENDING_REVIEW）；
   有 → 风险只升不降、repeat_count+1
   ▼
通知：班主任 → 个人顾问 → 部门主管（去重；正文不含心理原文）
   ▼
人工处置状态机：PENDING_REVIEW → CONFIRMED → HANDLING → CLOSED（可 DISMISS）
```

> 直接风险词告警在 AI 不可用时也保留（合法 H_DIRECT 信号）；情绪观测有效性（`is_valid`）与告警有效性分开建模，避免 UNKNOWN 情绪吞掉真实告警。

### 3.7 教务数据流（成绩 / 日程 / 提醒 / 进度）

```
【录入侧】员工（非 NEWCOMER + 负责范围）
   POST /employees/students/{id}/scores   → 写 student_score（data_source=MANUAL）
   POST /employees/students/{id}/schedules → 写 student_academic_schedule（MANUAL）
   POST /employees/application-cases      → 写 student_application_progress（申请进度）
   POST /employees/application-cases/{no}/events → 追加进度事件（STAGE/DETAIL/ASSIGNMENT）
   ▼
【查询侧】学生只读本人数据
   GET /me/scores → 读 student_score（生产排除 data_source=TEST）
   GET /me/schedules → 读 student_academic_schedule
   GET /application-cases → 读 student_application_progress（每 case_no 取最大 sequence_no）
   GET /application-cases/{no}/timeline → 同表按 sequence_no 升序
   ▼
【提醒】学生 PUT /me/schedules/{id}/reminder
   写 remind_at + reminder_revision+1（防旧任务重发）→ 定时任务按 revision 领取发送
```

### 3.8 升学意向数据流（增值转化）

```
学生对话识别升学意向（学生助手 UPGRADE_INTEREST）
   ▼
后端返回已发布项目列表 → 学生选择项目 → 确认卡
   ▼
POST /me/upgrade-interests（@idempotent）
   │  校验：confirmed、有 converted_lead_id、有 advisor、项目已发布
   ▼
写 crm_follow_up（follow_up_type=UPSELL_INTEREST、details={course_project_id}）
   + 通知个人顾问（related_type=lead）
   ▼
返回 { accepted, followUpId, advisorDisplayName }
```

> 不写 `crm_lead` 主表，只追加跟进事件并通知顾问跟进。

### 3.9 通知机制

```
业务动作 → notification.notify(...)
   │  ① 校验 category / related_type 白名单
   │  ② recipients 去重
   │  ③ INSERT ... ON CONFLICT DO NOTHING（recipient_user_id, business_event_key）
   │      → 同一 (接收人, 事件键) 只落一条，天然幂等
   ▼
不自行 commit，由外层 with_business_transaction 一起提交（业务状态与通知同生共死）
   ▼
前端 GET /me/notifications → 按 relatedType 跳转处理页
```

### 3.10 AI 助手通用数据流（Dify 调用与确认卡机制）

```
用户在前端悬浮窗发消息（AssistantDock.vue）
   ▼
POST /api/v1/assistants/{student|employee|visitor}/messages
   ▼
后端 service 组装 payload（只含授权后选取的上下文，绝不携带 JWT）
   │  学生：本人档案摘要 + 心理授权开关 + 已发布项目
   │  员工：最小身份能力提示 + 受控上下文
   │  访客：公开项目/活动摘要
   ▼
Dify Workflow（意图识别 → 草稿提取 → 契约校验 → 知识检索分支）
   ▼
返回 output_json → 后端 contracts.validate_* 二次校验（缺字段=澄清，坏输出=错误）
   ▼
后端分支：
   ① 授权查询（本人数据）→ 中文渲染返回
   ② 写操作 → 生成 proposal 确认卡（operation/preview/requestKey/confirmationToken/expiresAt）
   ③ 知识问答 → 返回 answer + sources（来自实际检索 metadata）
   ▼
用户点击「确认办理」→ 前端调用普通业务接口提交（携带 request_key + confirmation_token）
   ▼
后端重新鉴权 + 比对确认内容 + 幂等 + 事务执行
```

> 核心原则：**AI 只提议，后端鉴权执行，用户确认后才写库**。工作流不接受登录 JWT、不直接调用业务写接口、不自行声明 `confirmed=true`。

## 六、班主任视角功能详解

### 6.1 页面与菜单

班主任 = 有班级（`classTeacherOfIds`）的员工，`role=TEACHER`。菜单与顾问基本一致，但**默认隐藏「客户管理」**，侧重学生服务与关怀。

### 6.2 班主任核心功能与数据流

## 七、AI 助手架构与安全边界

### 7.1 六个 Dify 应用与后端配置

| 应用 | 工作流文件 | 后端配置键 |
|---|---|---|

| 企业助手 | `dify/wf_enterprise.yml` | `DIFY_ENTERPRISE_KEY` |
| 客户研判 | `dify/wf_profile.yml` | `DIFY_ASSESSMENT_KEY` |
| 报告助手 | `dify/m5_report_assistant.yml` | `M5_DIFY_ASSISTANT_KEY` |

统一输入 `payload_json`、统一输出 `output_json`，均为 JSON 字符串。

### 7.2 统一的「进 Dify → 出 Dify」管道

**通俗理解**：把 Dify 当成一个"外包的意图理解员"。后端把用户这句话 + 一段**裁剪过的上下文**打包成信封（`payload_json`）寄过去；Dify 拆开信封，让大模型判断"用户想干什么、还缺什么"，把判断结果装回信封（`output_json`）寄回来；后端拆开信封后**不轻信模型，会再校验一遍**，才决定是直接回答、还是出确认卡。

**进 Dify（后端 → Dify）**：

```
service 组装 payload（只放授权后选取的上下文，绝不含登录 JWT）
  → integrations/dify/__init__.py::run_workflow(audience, payload, user)
  → 按 audience 选应用 key（_AUDIENCE_KEYS）
  → client.py::DifyClient.run_workflow(key, {"payload_json": json.dumps(payload)}, user)
  → POST {base_url}/v1/workflows/run
      body = {"inputs":{"payload_json":"{...}"}, "response_mode":"blocking", "user":"..."}
```

**出 Dify（Dify → 后端）**：

```
Dify 返回 {"data":{"status":"succeeded","outputs":{"output_json":"{...}"}}}
  → client.py 校验 status=succeeded（超时/401/403/429/5xx/非JSON/failed → 对应 AI 异常）
  → run_workflow 把 output_json 字符串解析成 dict
  → 各适配器 _validate() + contracts.validate_*() 二次校验
  → 失败统一降级 aiStatus=UNAVAILABLE，保留表单路径
```

> 例外：M5 两个报告工作流用 **streaming（SSE）**，由 `m5_report_ai.py` 消费 `workflow_finished` 事件；其余 4 个用 blocking（一次请求等完整结果）。
>
> 一句话记住"进与出"：**进是 JSON 字符串（`payload_json`），出也是 JSON 字符串（`output_json`）**，中间不传登录态、数据库密码、知识库 UUID。

### 7.4 工作流内部结构（以学生助手为例）

```
start(核验入参 payload_json)
  → prepare(code：多轮上下文合并)
  → llm(提取受控业务意图与草稿)
  → sanitize(code：校验意图/字段/缺项/越界)
  → knowledge_gate(if-else)
       ├─ false → end(output_json，普通业务)
       └─ true  → knowledge(知识库检索)
                   → knowledge_context(code：核验实际来源)
                   → knowledge_llm(依据已核验资料回答)
                   → knowledge_validate(code：引用白名单)
                   → end_knowledge(output_json)
```

### 7.5 安全边界（贯穿所有助手）

1. **JWT 不进工作流**：登录令牌只在后端，工作流输入不含凭证。
2. **AI 不直接写库**：写操作先返回确认卡，用户确认后走普通业务接口。
3. **权限后端判定**：`context`、`actor` 或自然语言里声称的角色不能授权。
4. **引用只来自真实检索**：`sources` 由实际检索 metadata 生成，不采信模型自造 document_id。
5. **学生/员工知识库隔离**：学生绑定对外库，员工绑定内部库，不混用。
6. **失败降级**：AI 不可用返回 `UNAVAILABLE`，保留表单路径办理业务。

## 九、交付验证要点（如何确认数据流正确）

1. **留资**：全新手机号留资 → 201；重复提交同键 → 复用不报错；未选项目 → 进待分配池，顾问可认领。
2. **研判**：提交简历 → Dify 提取 → 顾问核对 → 规则给出 MATCH/NO_MATCH/NEEDS_INFO，不因 AI 抽错直接误判。
3. **转学生**：签约后生成学生账号 + 档案 + 项目关联，临时密码仅首次可见，重复提交不再给密码。
4. **请假**：请假重叠并发只接受合法请求；班主任审批后学生收到通知。
5. **工单**：提交→认领→解决→学生确认关闭→评价，重开次数正确。
6. **心理**：AI 不可用时直接风险词告警仍保留；撤回授权后立即停止情绪处理。
7. **助手**：AI 只出确认卡，不写库；换人/换对象/换内容/换版本/过期/重放都被拒绝。
