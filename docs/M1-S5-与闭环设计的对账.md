## 一、为什么要有这份

**问题**：我们实现到一半，规范文档可能有更新。
**不逐条对，会出现**：前端照规范写、后端实现不一致 → **联调时才发现，返工大**。

**所以**：把"规范写的"和"我们实现的"逐项对一遍，**发现差异立即修**。

## 五、怎么做的对账（可复用）

**给以后的人**：改了代码后怎么确认和规范一致？

```bash
# ① schema 逐字节比对
diff <(cat deploy/schema.sql) <(cat <规范>/数据库/schema.sql)

# ② 接口路径比对
#    - 取我们运行的 openapi.json
curl -s localhost:8000/openapi.json | python3 -c "..."
#    - 取规范 04 文档里的路径（正则抽 API 编号 + 方法 + 路径）
#    - 归一化参数名（{任意}→{x}）后比对

# ③ 枚举比对
grep -oE "IN \('[^)]*\)" deploy/schema.sql | sort > /tmp/ours
grep -oE "IN \('[^)]*\)" <规范>/数据库/schema.sql | sort > /tmp/spec
diff /tmp/ours /tmp/spec
```

## 六、注意事项

| ❌ 不要 | 为什么 | ✅ 应该 |
|---|---|---|
| 改接口路径不通知 | 前端/Dify 会 404 | 走变更流程（M1-S3） |
| 创建接口返回 200 | 不符合 REST 约定 | 201（已修 15 个） |
| 自己造 `request_id` 格式 | 日志系统无法索引 | 用 UUID |
| 只改代码不改文档 | 文档和实现分叉 | 一起改（本次已做） |
| 以为"接口数一样"就没问题 | 路径词序、参数名可能不同 | 归一化后逐条对 |
