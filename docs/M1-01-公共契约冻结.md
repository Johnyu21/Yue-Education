# 一、英文枚举（中英对照表）

## **为什么要用英文枚举**

好处：

1. 代码更干净  （`if role == "ADVISOR"` 比 `if role == "顾问"` 少一堆编码/输入法问题）
2. 框架生态保持一致 （几乎所有规范都建议"存储用英文、展示用本地化"）

**全项目存储与接口一律用英文**（`STUDENT`/`NEW`/`ADVISOR`），
**中文只用于界面展示**——前端拿英文值查下表翻成中文。

> 这份表**同时是前端映射表的来源**：前端照它写 `const XXX = { NEW:'新增意向', ... }`。

# 二、ID 格式

| 项 | 约定 | 原因 |
|---|---|---|
| **数据库** | `BIGINT`（自增主键） | — |
| **JSON 传输** | **十进制字符串**，如 `"1001"` | **JS 大整数精度只有 15~16 位，BIGINT 会丢精度** |
| **字段类型（前端）** | `string`，不是 `number` | 同上 |
| **示例** | `{"id": "1001", "userId": "21"}` | — |

> **这是最容易出错的一条**：后端如果直接返回数字 `1001`，前端 JS 处理到
> **超大 ID（> 2^53）就会出错**。所以**统一转字符串**。

# 三、时间格式

| 项 | 约定 |
|---|---|
| **数据库存储** | 一律 **UTC**（`TIMESTAMPTZ`） |
| **接口输出** | **ISO 8601 带时区**，如 `"2026-10-15T02:10:00Z"` |
| **纯日期字段** | `YYYY-MM-DD`，如 `"2026-10-15"`（如 `graded_at`） |
| **输入** | **必须带时区**，不接受无时区的裸时间 |
| **显示** | 前端转成北京时间（UTC+8）展示 |

> 例：数据库存 `2026-10-15T02:10:00Z` → 前端显示 `2026-10-15 10:10`（北京时间）。

# 四、统一响应与错误码

## 4.1 成功响应

```json
{
  "code": "OK",
  "message": "成功",
  "data": { "id": "1001" },
  "request_id": "3ab75064-0587-4150-970a-ff11d1c22588"
}
```

| 字段 | 说明 |
|---|---|
| `code` | `"OK"` 表示成功（**是字符串，不是数字 0**） |
| `data` | 真正的数据 |
| `request_id` | 每次请求唯一，**出问题拿它定位** |

## 4.2 失败响应

```json
{
  "code": "VALIDATION_ERROR",
  "message": "参数校验失败",
  "data": null,
  "errors": [{ "field": "mobile", "reason": "手机号格式不正确" }],
  "request_id": "3ab75064-0587-4150-970a-ff11d1c22588"
}
```

**`errors` 是字段级错误**——前端能精确标红哪个输入框。

## 4.3 错误码表

| HTTP | code | 什么时候用 |
|---|---|---|
| 400 | `INVALID_REQUEST` | 请求语义无法处理 |
| 401 | `AUTH_REQUIRED` / `TOKEN_EXPIRED` | 未登录 / 令牌失效 |
| 403 | `FORBIDDEN` | 角色没这个功能权限 |
| 404 | `NOT_FOUND` | 不存在**或不在对象范围内**（不暴露别人的数据） |
| 409 | `VERSION_CONFLICT` | 版本冲突（并发） |
| | `STATE_CONFLICT` | 状态不允许（如重复审批） |
| | `DUPLICATE_RESOURCE` | 重复（如手机号已存在） |
| | `EVENT_FULL` | 活动名额满 |
| 422 | `VALIDATION_ERROR` | 字段校验失败 |
| 429 | `RATE_LIMITED` | 限流 |
| 502 | `AI_BAD_RESPONSE` | Dify 返回了但不符合约定 |
| 503 | `AI_UNAVAILABLE` | Dify / 模型不可用 |
| 504 | `AI_TIMEOUT` | AI 超时（预算 45 秒） |
| 500 | `INTERNAL_ERROR` | 未预期异常（**不返回堆栈/ SQL / 密钥**） |

> **404 的细节（重要）**：**"对象不属于你"也返回 404，不是 403**——
> 这样别人无法通过"403 还是 404"探测出"这个 ID 存在"。**这是防信息泄露的标准做法。**

## 4.4 分页格式

```
请求：GET /api/v1/crm/leads?page=1&page_size=20

返回：{ "code":"OK", "data": { "items":[...], "total":135, "page":1, "page_size":20 } }
```

| 参数 | 约定 |
|---|---|
| `page` | 从 1 开始 |
| `page_size` | 默认 20，最大 100 |
| 排序 | **稳定排序**：`created_at` + `id` 一起决定（防分页漏项） |
| 空列表 | **返回 200 + 空数组**，不用 404 |

# 五、一个完整的请求/响应样例（全员照此解析）

**场景**：员工登录。

### 请求
```http
POST /api/v1/auth/login
Content-Type: application/json

{ "username": "advisor01", "password": "******" }
```

### 成功响应（200）
```json
{
  "code": "OK",
  "message": "成功",
  "data": {
    "access_token": "eyJhbGciOi...",
    "token_type": "Bearer",
    "expires_in": 7200,
    "user": {
      "id": "21",
      "username": "advisor01",
      "realName": "李四",
      "userType": "EMPLOYEE",
      "employeeRole": "ADVISOR",
      "deptId": "3"
    }
  },
  "request_id": "3ab75064-0587-4150-970a-ff11d1c22588"
}
```

### 失败响应（401）
```json
{
  "code": "AUTH_REQUIRED",
  "message": "用户名或密码错误",
  "data": null,
  "errors": [],
  "request_id": "3ab75064-0587-4150-970a-ff11d1c22588"
}
```

> **注意三点**：① `id` 是**字符串** `"21"`；② `employeeRole` 是**英文** `"ADVISOR"`；
> ③ 前端拿到 `employeeRole` 后，**查 1.1 的表翻成"顾问"显示**。

# 六、DTO 白名单（防止越权）

**规则**：**写入请求只接受白名单字段，未声明的字段一律拒绝。**

```json
// 客户端想偷偷提权，多传了 role 和 deptId
POST /crm/leads
{ "name":"张三", "mobile":"138...", "role":"ADMIN", "deptId":"1" }
        ↓
// 后端：只认 name/mobile，多出来的 role/deptId 直接忽略或拒绝
```

**为什么**：如果后端图省事直接 `data → model`，客户端就能**通过多传字段给自己改权限**。
**这是最常见的越权漏洞之一**，必须在 M1 层堵死。

**权限相关字段永不接受客户端传入**：`role`、`employeeRole`、`deptId`、`userId`、
`can_handle_feedback`、`psych_access_enabled`——**一律由后端按登录身份决定**。
