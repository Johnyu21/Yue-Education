## 二、设计说明

### 2.1 为什么需要"单实例锁" ⭐

**问题**：如果起了两个后端进程（或以后上多副本），
**定时任务会同时跑两遍** → 同一个提醒发两次。

```
进程 A 扫描 → 发现提醒 → 发通知
进程 B 扫描 → 发现同一个提醒 → 又发一次   ← 学生收到两条
```

**所以**：用 **PostgreSQL 咨询锁（`pg_try_advisory_lock`）**：
- 同一时刻**只有一个实例**能跑同一个任务
- 拿不到锁的**直接跳过**（非阻塞，不排队）

**验证过**：
```
✅ test_定时任务扫描不重复发通知
   连跑两次 → 同一提醒只产生 1 条
```

### 2.2 为什么用数据库锁而不是 Redis

| 方案 | 需要额外服务 | 进程挂了会死锁吗 |
|---|---|---|
| **PostgreSQL 咨询锁** | ❌ 不需要 | ✅ 不会（锁随连接释放） |
| Redis 分布式锁 | ✅ 要装 Redis | ⚠️ 要设过期时间，否则死锁 |

**你们已经跑着 PostgreSQL** —— **少一个依赖少一个故障点**。

### 2.3 为什么 event_key 带时间戳

跟进提醒的 key：`lead:12:followup:1730000000`（到期时间戳）

**为什么带时间戳**：
- 同一次提醒 → key 相同 → 只发一次 ✅
- **改了下次跟进时间** → 时间戳变了 → **新的一次提醒** ✅

**这样"同一件事只发一次"和"新的事要发"两不误。**

### 2.4 为什么发送前要"复查状态"

**问题**：扫描到"该提醒了"，但**在发送前的这几毫秒里，用户取消了**。
如果不复查，会**发出一个已取消事项的提醒**。

**所以**：发之前**再查一次状态**（`status == 'SCHEDULED'`）。

### 2.5 为什么默认关闭

**问题**：定时任务会**后台跑 + 占数据库连接**。
开发时**不想要**（影响调试、浪费资源）。

**所以**：默认 `SCHEDULER_ENABLED=false`，
**要用时手动开**。**多实例部署时只在一个实例上开。**

## 四、使用方式

### 4.1 开启

```bash
# .env 里加
SCHEDULER_ENABLED=true
SCHEDULER_INTERVAL=60        # 秒
```

**⚠️ 多实例时只在其中一个实例开**（有锁兜底，但仍不推荐都开）。

### 4.2 现有任务

| 任务 | 扫什么 | 间隔 |
|---|---|---|
| `scan_schedule_reminders` | `remind_at` 到期的日程 | 60 秒 |
| `scan_followup_reminders` | `next_follow_up_at` 到期的线索 | 120 秒 |

### 4.3 加新任务

```python
from app.core.scheduler import with_advisory_lock, LOCK_IDS, run_periodically

@with_advisory_lock(LOCK_IDS["my_task"], "my_task")
def my_task(db):
    rows = db.execute(text("...")).all()
    for r in rows:
        notify(db, f"xxx:{r.id}:remind:1", [r.user_id],
               category="SYSTEM", title="提醒", content="...")
    db.commit()

# 注册到 start_all()
```

**⚠️ 加任务要：**
1. 在 `LOCK_IDS` 里加锁编号（**全局唯一**）
2. 用稳定的 `event_key`（**保证幂等**）
3. 在 `start_all()` 里注册

## 五、注意事项

| ❌ 不要 | 为什么 | ✅ 应该 |
|---|---|---|
| 每个实例都开定时任务 | 重复发通知（锁能兜但不建议） | 只在一个实例开 |
| `event_key` 用随机值 | 去重失效 → 重复发 | 用稳定业务标识 |
| 扫描完不复查状态 | 发出已取消事项的提醒 | 发送前再查一次 |
| 任务里调 Dify 且不设超时 | 卡住后面的扫描 | 设超时 + 放事务外 |
| 锁编号重复 | 两个任务互斥（本该并行） | `LOCK_IDS` 里唯一 |
| 任务里 `while True` 不设间隔 | 打满 CPU | 用 `run_periodically` |

### ⚠️ 两条提醒

1. **`SCHEDULER_ENABLED` 默认是关的** —— 本地开发不需要开，
   测试定时任务时单独调函数（如 `scan_followup_reminders()`）即可。

2. **任务里的通知也走 `notify`** —— 所以同样遵守
   "event_key 唯一"和"跟事务一起提交"的规则（见 M1-07）。
