## 二、设计说明

### 2.1 为什么必须有它

**问题**：「签约转学生」要同时做 5 件事：

```
① 建账号      →  sys_user
② 建档案      →  student_profile
③ 建课程关联  →  student_course_enrollment
④ 改线索状态  →  crm_lead (FOLLOWING → SIGNED)
⑤ 写跟进记录  →  crm_follow_up
```

**如果第 ③ 步失败**（比如项目 id 填错），前两步**已经写进数据库了** →
出现"学生账号建了，但线索还是跟进中"的**脏数据**，人工都不知道怎么修。

**有了事务**：第 ③ 步失败 → **①② 自动撤销**，数据库回到操作前的样子。

### 2.2 为什么还要"翻译异常"

**问题**：数据库报的错是给开发看的，不是给用户看的：

```python
# 直接抛给用户
"duplicate key value violates unique constraint crm_lead_mobile_key"
# ↑ 用户看不懂，还泄露了表名和字段名（安全隐患）
```

**所以翻译成人话**：
```python
"数据已存在（可能重复提交）"     # DuplicateResourceError → 409
"关联数据不存在或状态不允许"     # StateConflictError → 409
```

**这样**：既不影响用户理解，又**不泄露数据库结构**。
而且**不会返回 500**（500 通常是"代码没考虑到的错"，会被记为 bug）。

### 2.3 为什么不用 SQLAlchemy 自带的 `begin()`

**能用，但不够**：
- 它不翻译异常（错误直接冒出去变 500）
- 没有"结果对象"（业务代码拿不到"是否提交成功"）

**所以包一层**，业务代码写起来更省事，也统一了错误处理。

### 2.4 为什么和 `safe_commit` 分开

| 场景 | 用哪个 |
|---|---|
| **多表操作**（转学生、审批+通知） | `with_business_transaction` |
| **单表简单写**（改个状态） | `safe_commit` |

**分开是因为**：多表需要"异常翻译"（错误更复杂），
单表用不着翻译（简单写一般不会撞复杂约束）。

### ⭐ 核心验证：中途失败全部回滚

**实测过程**：
```
操作前：tx_ 开头的账号 = 0 个
开始事务：
  ① 建账号 tx_stu2    → 成功
  ② 建档案            → 成功
  ③ 建课程关联（故意用不存在的项目 id）→ 💥 失败
事务回滚
操作后：tx_ 开头的账号 = 0 个  ✅ 一个都没留下
```

**这就是事务的价值** —— 数据库不会留下"一半的操作"。

## 四、使用方式

### 4.1 多表操作（转学生、审批+通知）

```python
from app.core.transaction import with_business_transaction

def convert_lead_to_student(db, lead, project_id, req):
    """签约转学生 —— 5 张表要么全成、要么全败"""
    with with_business_transaction(db):
        account = create_student_account(db, lead)          # ①
        profile = create_student_profile(db, account, lead) # ②
        enroll = create_enrollment(db, profile, project_id) # ③
        lead.status = "SIGNED"                               # ④
        lead.signed_at = now()
        add_follow_up(db, lead, "SIGNED")                    # ⑤
    # 到这里才真正写进数据库；中途任何异常 → 全部回滚
    return account, profile
```

### 4.2 单表简单写

```python
from app.core.transaction import safe_commit

def update_lead_status(db, lead, new_status):
    with safe_commit(db):
        lead.status = new_status
        lead.version += 1
```

### 4.3 配合乐观锁（M3 用）

```python
from app.core.errors import VersionConflictError

def update_with_version(db, lead, expected_version, new_status):
    with with_business_transaction(db):
        rows = db.execute(text("""
            UPDATE crm_lead SET status=:s, version=version+1
            WHERE id=:i AND version=:v
        """), {"s": new_status, "i": lead.id, "v": expected_version}).rowcount
        if rows == 0:
            raise VersionConflictError("数据已被他人修改，请刷新后重试")
    # ⚠️ 抛异常 → 事务自动回滚
```

## 五、注意事项

| ❌ 不要 | 为什么 | ✅ 应该 |
|---|---|---|
| 多表操作分开 commit | 中途失败留脏数据 | 包在一个 `with_business_transaction` 里 |
| 在事务里调 Dify / 发 HTTP | 外部调用慢，会**长时间占着数据库锁** | **AI 调用放事务外**，先算好再写 |
| `try/except` 吞掉事务异常 | 事务已经 rollback，但你以为成功了 | 让它抛，让调用方处理 |
| 事务里做耗时操作（循环几万次） | 锁持有太久，其他人被阻塞 | 事务只包"必须原子"的写操作 |
| 忽略 `VersionConflictError` | 说明有人并发改了，你的数据是旧的 | 提示用户刷新重试 |

### ⚠️ 两条最容易错的

1. **AI 调用绝不能放事务里** —— Dify 一次可能几秒，
   事务期间**数据库行被锁着**，别人全被堵住。
   **正确做法**：先在事务外调 Dify 拿结果，再开事务写库。

2. **通知和业务状态要同一个事务** —— M1 文档明确要求
   "业务状态与站内通知同事务"。
   如果分开：状态改了、通知没发出去 → 老师永远收不到。
