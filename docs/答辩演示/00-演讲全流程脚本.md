# 第一部分：项目背景与需求确定（3 分钟）

## 1.1 业务背景

留学教育服务的典型业务链条很长：

```
市场获客 → 咨询接待 → 客户跟进 → 意向研判 → 签约
   → 学生入学 → 教务与申请服务 → 毕业/升学
```

这条链条上有四类典型问题：

| 痛点 | 具体表现 |
|---|---|
| 获客分散 | 官网表单、AI 客服、线下活动、手工录入，客户信息散落在不同地方 |
| 跟进不可追溯 | 谁跟进了、跟进到哪一步、为什么流失，缺少统一记录 |
| 服务链条断点 | 签约后学生档案、成绩、日程、申请进度、请假、投诉分散管理 |
| 数据敏感且角色多 | 客户、学生、投诉、心理数据敏感，顾问/班主任/主管/管理员权限不同 |

**一句话总结**：

> 业务不是缺一个「页面」，而是缺一条**可追踪、可审核、可审计**的服务链路。

## 1.2 如何根据业务确定需求（四步法）

需求不是拍脑袋列的，我们按四步收敛：

### 第一步：按角色梳理场景

| 角色 | 核心诉求 |
|---|---|
| 访客 | 了解项目、政策、活动，能咨询、留资、报名 |
| 学生 | 看自己的档案、成绩、日程、申请进度，能请假、反馈 |
| 顾问 | 接待客户、跟进、研判、签约、写日报 |
| 班主任 | 管本班学生、审批请假、关注心理状态 |
| 主管 | 审核日报、分配客户、看部门报告 |
| 管理员 | 管账号、组织、项目活动、全域数据 |

> 我们先把「谁在什么场景下要做什么」列清楚，再决定接口和数据表。

### 第二步：把场景串成主链路

```
访客留资 → 线索池 → 顾问认领 → 跟进 → 研判 → 签约转学生
   → 学生服务 → 日报 → 报告
```

每条链路都明确：**入口、状态、谁能操作、失败怎么办**。

### 第三步：冻结公共契约

在写业务代码前，先统一：

- 统一响应格式（`code / message / data / errors / request_id`）
- 统一 ID 规则（全部用字符串，UUID 不转整数）
- 统一时间规则（入库 UTC，业务按 Asia/Shanghai）
- 统一错误码与 HTTP 状态
- 统一权限模型（角色 + 组织关系 + 数据敏感级别）
- 统一幂等与确认令牌

> 这一步的意义是：五个模块并行开发时，接口不会各写各的。

### 第四步：定义可验收的标准

- 每个业务链有状态机（如线索 `NEW → FOLLOWING → SIGNED / LOST`）
- 每个写操作有并发与幂等要求
- 每个敏感数据有独立授权
- 每个报告指标有明确口径（`formula` 字段）
- 用自动化测试固化：后端 160+ 项测试、前端组件/契约测试

## 1.3 需求边界（做什么、不做什么）

**做**：

- 访客获客、客户研判、签约转学生
- 学生档案、成绩、日程、申请进度
- 行政申请、售后工单、心理关怀
- 日报审核、6 类报告、Word/PDF 导出
- 四类 AI 助手（访客、员工、学生、报告）

**明确不做 / 明确降级**：

- 不做真实支付与合同签署（线下完成，系统只记录合同参考号）
- 不冒充外部教务/签证系统实时同步（标注「内部登记」）
- AI 不可用时不做假数据（保留确定性指标与表单）
- 心理数据不做诊断，只做观测与人工复核提醒

## 1.4 本部分话术（可直接照读）

> 我们的需求不是从「想做一个管理系统」开始的，而是从四类角色、一条主链路开始的。
> 先把访客、学生、顾问、班主任、主管、管理员各自要做什么列清楚，再把它们串成获客到报告的链路；
> 在写代码前先冻结公共契约，最后用状态机和测试把需求变成可验收的标准。
> 同时我们明确了很多「不做」的边界，比如不做真实支付、不冒充外部系统同步、AI 不可用时不做假数据。

# 第二部分：开发架构设计（3 分钟）

## 2.1 总体架构图（可照着画）

```
┌─────────────────────────────────────────────────────────┐
│                        浏览器                            │
│  访客站（项目/政策/活动/AI客服） │ 工作台（员工/学生）      │
└──────────────────────────┬──────────────────────────────┘
                           │ HTTP / JSON
┌──────────────────────────▼──────────────────────────────┐
│                  Vue 3 + TypeScript + Vite               │
│  App.vue 单壳三态：访客态 / 登录态 / 工作台态              │
│  BusinessWorkspace 按 resources.ts 契约动态渲染            │
└──────────────────────────┬──────────────────────────────┘
                           │ REST /api/v1
┌──────────────────────────▼──────────────────────────────┐
│                    FastAPI 应用（单入口）                  │
│  controllers（薄路由）                                     │
│      ↓                                                    │
│  services（状态机 / 事务 / 权限 / AI 编排）                 │
│      ↓                                                    │
│  repositories（带范围的查询组装）                          │
│      ↓                                                    │
│  models（SQLAlchemy ORM）                                 │
│                                                           │
│  core：权限 Scope / 响应 / 错误码 / 幂等 / 确认令牌 / 调度   │
└───────────────┬─────────────────────────┬────────────────┘
                │                         │
┌───────────────▼──────────┐   ┌──────────▼────────────────┐
│ PostgreSQL（独立业务库）   │   │ Dify 工作流（6 个能力）      │
│ 19 基础表 + M5 增量表      │   │ 访客/研判/企业/学生/报告/助手 │
└──────────────────────────┘   └───────────────────────────┘
```

## 2.2 后端为什么这样分层

| 层 | 职责 | 为什么单独一层 |
|---|---|---|
| controllers | 解析入参、取身份、调 service、统一返回 | 路由保持「薄」，不混业务规则 |
| services | 状态机、事务、权限、AI 编排 | 同一业务可被 HTTP、助手、定时任务复用 |
| repositories | 带数据范围的查询组装 | 权限条件只写一次，避免各处漏过滤 |
| models | ORM 映射 | 表结构集中管理 |
| core | 横切能力 | 配置、权限、幂等、确认令牌统一 |

**关键设计**：权限不是前端隐藏按钮，而是 `core/permissions.py` 把「本人」翻译成 SQL 的 `WHERE` 条件，范围外一律返回 404。

## 2.3 前端为什么是「单壳三态」

```
App.vue
├─ 访客态   → VisitorPages.vue（首页/项目/政策/活动/关于）
├─ 登录态   → 登录页 + 视频背景
└─ 工作台态 → 顶栏 + 侧边菜单 + 业务页面
```

- 访客和员工共用一套代码，减少重复
- 工作台页面由 `api/resources.ts` 配置驱动：一个资源 = 路径 + 表格列 + 可执行动作 + 权限门禁
- 复杂页面（日报、报告、学生详情）用专用组件

## 2.4 数据与权限设计

**角色来源**（不是硬编码在用户表里）：

| 身份 | 来源 |
|---|---|
| 学生 | `user_type = STUDENT` |
| 新人/顾问/高级顾问/管理员 | `employee_role` |
| 部门主管 | `sys_department.head_user_id` |
| 班主任 | `sys_class.head_teacher_id` |

**数据范围**：

| 角色 | 范围 |
|---|---|
| 管理员 | 全域普通业务 |
| 主管 | 本部门（不含子部门） |
| 顾问 | 本人客户 / 本人负责学生 |
| 学生 | 本人档案 |
| 范围外 | 404，不暴露数据存在性 |

**敏感数据双闸门**：

- 投诉：`can_handle_feedback`
- 心理：`psych_access_enabled`，**管理员也不自动获得**

## 2.5 AI 架构：只建议、不落库

```
业务请求 → service 组装受控上下文 → 事务外调用 Dify
   → 返回草稿/提议 → 权限签名复核 → 前端确认
   → 调普通业务接口写库
```

- Dify 是唯一 AI 出口，Key 只在后端
- 四种助手：访客客服、企业助手、学生助手、报告助手
- 失败统一降级 `UNAVAILABLE`，不冒充成功

## 2.6 技术选型理由（一句话版）

| 选择 | 理由 |
|---|---|
| FastAPI | 类型友好、OpenAPI 自动生成、适合契约驱动 |
| PostgreSQL | 事务、行锁、JSONB、复杂统计，适合业务+报告 |
| SQLAlchemy | 显式事务与条件更新，便于控制并发 |
| Vue 3 + TS | 单页交互流畅，类型约束减少契约错误 |
| Dify | 工作流可视化，业务方可维护提示词与节点 |

## 2.7 本部分话术

> 架构上我们做了三个关键选择：
> 第一，后端严格分层，控制器薄、服务厚，权限收敛到 SQL 层；
> 第二，前端是单壳三态，访客和员工共用一套代码，页面由契约配置驱动；
> 第三，AI 只有唯一出口，而且只产出草稿或提议，写库必须本人确认。

# 第三部分：遇到的问题（4 分钟）

> 这一部分讲真实踩过的坑。每个问题按「现象 → 原因 → 解决 → 验证」四步讲。

## 问题一：AI 直接写库，越过了用户确认

**现象**：早期学生助手把登录 JWT 传给 Dify 工作流，工作流自己生成 `request_key` 和 `confirmed=true`，直接 POST 业务接口。

**原因**：把「AI 能调用接口」当成了「AI 能代表用户确认」。

**解决**：

- 后端改为「授权查询 + 签发确认卡」
- 登录令牌不进入工作流
- AI 只能返回 `Proposal` + `confirmation_token`
- 前端确认后，由 `proposals.ts` 调真实业务接口
- 确认令牌绑定：主体、操作、对象、载荷、版本

**验证**：测试覆盖「生成写提议不改业务表」「换人/换操作/改内容/重放均拒绝」。

> **答辩一句话**：AI 可以帮你想、帮你填，但不能替你签字。

## 问题二：权限只在页面上藏了按钮

**现象**：通讯录接口只要求登录，学生也能拿到员工信息；公开活动传入 `DRAFT` 能读到草稿；心理修正把普通顾问当成主管；售后转派没有校验主管身份。

**原因**：权限写在了前端或控制器，没有落到查询条件和业务服务。

**解决**：

- 把数据范围下沉到 `permissions.py`，生成 SQL 条件
- 越权统一 404
- 敏感能力独立授权（`can_handle_feedback` / `psych_access_enabled`）
- 心理修正增加真实主管关系或管理员 + 专项授权
- 售后转派限定主管/管理员，并校验目标员工状态、能力和部门

**验证**：跨角色权限测试、越权 404 测试、撤权后历史报告拒绝读取。

> **答辩一句话**：前端隐藏按钮不是权限，数据库查询条件才是。

## 问题三：并发下数据会重复或超卖

**现象**：

- 两个请求同时更新同一客户，后写覆盖先写
- 同一学生并发提交重叠请假，两条都通过
- 活动最后一个名额并发报名，出现超卖
- 网络重试重复创建学生账号

**原因**：先读版本、再无条件写入；检查发生在锁之前；幂等只按全局 key。

**解决**：

- 更新用 `WHERE version = 旧版本` 条件更新，冲突返回 409
- 请假先锁学生主行，再查重叠
- 报名锁活动行并锁内复查名额
- 幂等绑定「主体 + 操作 + 内容摘要」，相同键不同内容返回 409
- 签约转学生一个事务完成账号、档案、项目、状态、跟进、通知

**验证**：双连接并发测试、重试测试、名额竞争测试。

> **答辩一句话**：并发正确性不能靠「先查一下再写」，要靠数据库条件更新和行锁。

## 问题四：日报有两个事实源

**现象**：旧的 `employee_daily_report` 和新的 `m5_daily` 同时存在，ID、日期、返回字段不一致，报告统计口径分裂。

**原因**：模块并行开发时各写了一套日报。

**解决**：

- 确定 `m5_daily` 为唯一写入源
- 旧表只读过渡，历史数据映射迁移
- 审核通过写入不可变快照 `m5_daily_revision`
- 后续报告只用「最近通过的版本」

**验证**：审核历史、旧通过版本、撤权、导出的回归测试。

> **答辩一句话**：一份数据只能有一个事实源，否则所有统计都会打架。

## 问题五：报告的数字和正文会「漂移」

**现象**：生成预览后，业务数据发生变化，保存时重新统计，导致正文说的和指标数字不一致。

**原因**：保存时重新计算，没有绑定生成时的快照。

**解决**：

- 预览时持久化 `m5_report_snapshot`（请求条件 + 指标 + 授权签名）
- 保存时必须带本人 `snapshot_id`，且条件一致
- 报告记录访问时复核当前授权与学生范围
- AI 只写 `narrative`，数字全部由后端确定性计算

**验证**：快照同源测试、业务变更后历史报告不漂移测试、撤权测试。

> **答辩一句话**：报告一旦生成，就应该是一张「冻结的照片」，而不是实时重算。

## 问题六：Dify 本地改了，线上没生效

**现象**：本地 YML 已修正，线上仍报 `JSONDecodeError`；模型输出带 `<think>` 思考标签，JSON 解析失败。

**原因**：

- 只改本地文件，没有在 Dify 控制台重新发布
- 模型输出格式不受控

**解决**：

- 明确「保存 ≠ 发布」，必须点发布才更新 API 版本
- 代码兼容 `<think>` 标签和 ```json 代码围栏
- 严格校验输出字段：报告必须有非空 `narrative`
- 解析失败不冒充成功，统一降级并保留指标
- 用离线契约脚本回放真实模型输出

**验证**：`check_m5_dify_contract.py` 14 项离线测试；真实 API 探测脚本 `probe_m5_dify.py`。

> **答辩一句话**：AI 的输出必须当成「不可信输入」，要做结构校验和降级。

## 问题七：测试把共享库的数据删了

**现象**：早期测试使用共享库，夹具里有范围较大的删除条件，可能误删业务数据。

**原因**：没有独立测试库，测试数据隔离不足。

**解决**：

- 独立测试库 `yue_education_test`
- 每轮随机 schema，测试后回收
- 硬性检查库名与环境
- 禁止对共享业务库运行破坏性夹具

**验证**：测试 schema 残留检查、库名护栏测试。

> **答辩一句话**：测试的第一原则是不伤害真实数据。

## 3.8 问题总结（收尾话术）

> 这些问题看起来是七个，本质上是三类：
> 第一类是**边界问题**——AI 的边界、权限的边界、测试的边界；
> 第二类是**一致性问题**——并发的版本、日报的事实源、报告的快照；
> 第三类是**外部依赖问题**——Dify 的发布版本和不可信输出。
> 我们的处理原则是：边界要硬、数据要单一事实源、外部依赖要可降级。

# 第四部分：项目演示（6–8 分钟）

> 演示顺序：**访客 → 顾问 → 主管 → 学生 →（可选）班主任/管理员**
> 每一步都给出「操作 + 话术」，照着做即可。

## 4.1 演示路线图

```
① 访客站（不登录）
   首页 → 项目详情 → 活动 → AI 客服 → 留资

② 顾问（ui_advisor）
   客户管理 → 公共池认领 → 跟进 → 研判 → 学生服务 → 日报

③ 主管（ui_head）
   日报审核 → 报告中心 → 打开主管周报 → 导出

④ 学生（13911110002）

## 4.2 访客端演示（约 2 分钟）

**操作步骤**

# 第五部分：工作流（3 分钟）

## 5.1 主链路工作流（一张图讲完）

```
① 获客
访客浏览项目/活动/AI客服
   → 留资（手机号规范化 + 幂等）
   → 线索进入公共池（按意向项目路由部门）

② 跟进与研判
顾问认领 → 跟进记录 → 补充资料
   → 发起研判（审核通过的规则 + 确定性判定）
   → MATCH / NO_MATCH / NEEDS_INFO

③ 签约转化
签约 → 一个事务完成：
   学生账号 + 学生档案 + 项目关联 + SIGNED 状态 + 跟进 + 通知

④ 学生服务
档案 / 成绩 / 日程 / 申请进度 / 请假 / 反馈 / 心理关怀

⑤ 日报
填写 → AI 整理草稿 → 保存 → 提交 → 主管通过/退回 → 通过快照

⑥ 报告
6 类报告：确定性指标 + AI 正文 + 不可变快照 → 核对 → 保存 → 导出
```

## 5.2 分角色工作流矩阵

| 角色 | 入口 | 核心动作 | 数据范围 |
|---|---|---|---|
| 访客 | 访客站 | 浏览、AI 咨询、留资、报名 | 已发布项目/活动 + 本人提交 |
| 学生 | 我的服务 | 看档案/成绩/日程/进度、申请、反馈、授权 | 本人 |
| 顾问 | 客户管理 | 认领、跟进、研判、签约、日报 | 本人客户/学生 |
| 班主任 | 学生服务 | 本班管理、行政审批、心理关注 | 本班 |
| 主管 | 日报/报告 | 审核、分配、6 类报告 | 本部门 |
| 管理员 | 账号管理 | 账号、组织、项目活动、全域数据 | 全域普通业务 |

## 5.3 状态机一览（评委爱问）

| 业务 | 状态流转 |
|---|---|
| 客户线索 | `NEW → FOLLOWING → SIGNED`；`FOLLOWING → LOST → FOLLOWING` |
| 日报 | `DRAFT → SUBMITTED → APPROVED`；`SUBMITTED → RETURNED → DRAFT`；`SUBMITTED → DRAFT`（撤回） |
| 行政申请 | `PENDING → APPROVED / REJECTED / CANCELLED` |
| 售后工单 | `PENDING → PROCESSING → RESOLVED → CLOSED`；`RESOLVED → 学生重开 → PROCESSING` |
| 心理预警 | `PENDING_REVIEW → CONFIRMED / HANDLING / DISMISSED / CLOSED` |
| 报告 | `DRAFT`；主管周报可 `SUBMITTED`，提交后不可改 |

## 5.4 数据流与权限流

```
业务写入
  → service 校验状态机与权限
  → repository 带 Scope 条件写库
  → 同一事务写通知/跟进/快照
  → 返回统一响应

业务查询
  → 身份解析（角色 + 部门 + 班级 + 顾问关系）
  → build_scope 生成 WHERE 条件
  → 范围外 404
```

**AI 数据流**：

```
业务事实（受控、脱敏）→ Dify → 草稿/提议
   → 权限签名复核 → 用户确认 → 普通业务接口
```

## 5.5 收尾话术（30 秒）

> 最后用一句话总结这套工作流：
> **访客进得来、顾问跟得住、主管审得清、学生用得上、报告出得去。**
> 支撑它的三个原则是：AI 只建议不落库、权限在数据库层收敛、外部依赖可降级。
> 我的汇报到这里，谢谢各位老师。

# 附录 C：可能被问到的问题与回答

| 问题 | 回答要点 |
|---|---|
| 为什么不用微服务？ | 当前团队规模和业务耦合度更适合单体分层；权限、事务、部署都更简单，后续可按模块拆分 |
| AI 会不会编数据？ | 不会。指标和事实由后端确定性计算，AI 只写叙述；输出还要通过结构校验 |
| Dify 挂了怎么办？ | 统一降级 `UNAVAILABLE`，保留指标、表单和手工办理路径 |
| 权限怎么保证？ | 角色 + 组织关系 + 敏感能力三重组合，落到 SQL 条件；越权 404 |
| 并发怎么保证？ | 数据库条件更新、行锁、唯一约束、幂等键；双连接测试验证 |
| 报告数字准不准？ | 每个指标有 formula；生成时冻结快照；保存和导出引用同一快照 |
| 心理数据安全吗？ | 独立授权，管理员也不自动获得；未授权不处理；撤回后停止 |
| 测试怎么做的？ | 独立测试库 + 随机 schema；后端 160+ 项测试；前端组件/契约测试；浏览器流程检查 |
