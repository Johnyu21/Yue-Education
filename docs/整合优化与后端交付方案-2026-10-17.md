# 粤教智能留学项目整合优化与后端交付方案

评审日期：2026-10-17  
版本：V1 评审稿  
当前阶段：审查与方案设计，尚未开始修改业务代码

本方案以原始客户需求、小组现有实现和当前用户确认的范围为依据。建议保留 FastAPI、SQLAlchemy、PostgreSQL 与现有业务分层，优先修复整合断点、权限、并发和数据口径，再补齐可验收业务。Dify 工作流尚未搭建，本轮交付应保证后端业务独立运行，并交付可直接对接工作流的契约、适配器和离线验证材料。

## 一 已确认范围与审查结论

### 1 已由用户确认

- 本轮完整交付后端、接口文档、测试和部署材料。前端架构由用户维护，后续另行整合；不重建当前前端，也不迁入其他实验前端。
- 员工日报提交后，由主管审核，通过内容才能进入汇总。
- 管理员可查看全域普通经营数据；心理和投诉仍需独立专项授权。
- 测试环境和验收清单由本轮设计。目前没有既定测试环境、验收清单或已指定的历史数据保留要求。
- 本轮先提交方案，用户过目确认方案后才开始实施。对以上范围的确认不等于已经批准开始修改业务代码。

### 2 总体判断

现有代码具有可复用的业务基础：统一认证与响应、客户获客、CRM、签约转学生、行政申请、投诉、心理观测和内部申请进度已有实现。但当前状态属于多个模块合并后的开发版本，还不满足后端完整交付标准。

主要阻碍是：常规入口没有装配 M5；日报事实源分裂；学生助手的执行方向与确认机制不一致；部分权限边界和并发保障未落到实际写入；测试与部署材料不完整；原始需求和小组缩减范围没有形成统一验收基线。不能依据文档中的历史“全部通过”标记判断当前整合代码已经通过验收。

未发现文本形式的 Git 冲突标记。这里的主要冲突是业务设计、入口、接口契约与数据来源冲突，不能只靠搜索冲突标记解决。

### 原始需求与既有缩减决策的处理建议

小组文档曾明确“成绩只读、仅 TEST 数据”“语音暂缓”“进度仅内部人工登记”。这些是旧版本的取舍，不能直接称为原始需求已经完成。

建议本轮后端增加员工授权的成绩录入/修订与教务日程维护或批量导入，数据来源标为 MANUAL，并调整原 DDL 中仅 TEST 的约束；学生保持只读。外部教务、CRM 或签证系统的实时同步先提供独立适配接口和幂等机制，未接供应商时明确显示内部登记来源，不编造外部同步结果。

语音提供可配置的转写适配器、文件校验、超时与功能状态。没有供应商时返回明确的功能不可用状态并保留文字入口。若验收要求真实语音或真实外部系统同步，必须在第二层集成验收中完成，不能用模拟结果替代。此处为本方案的范围建议，随整份方案一并评审。

## 五 目标架构与整合原则

### 1 保留分层并收口公共能力

继续使用 controller → service → repository → model。controller 负责 HTTP 入参、依赖和输出；service 负责权限、状态机与事务边界；repository 负责带范围的读取和原子写入。跨模块操作复用业务服务，不跨 HTTP 调自己的服务。

公共配置、错误码、请求 DTO 基类、权限策略、确认凭据、幂等、时间工具和 AI 适配统一管理。移除“因为不能改其他组员文件所以加一层桥”的临时技术隔离，前提是先保存基线、明确兼容范围并通过回归。

不做无收益的大规模重命名，不为了形式拆分所有文件。先修复实际运行路径；对外 API 迁移有兼容说明和测试，不能只改新路径。

### 2 统一权限模型

权限由三部分组合：登录身份与岗位能力、实时组织/顾问/班级关系、数据敏感级别。主管身份只来自 sys_department.head_user_id，班主任只来自 sys_class.head_teacher_id。

| 主体 | 普通业务范围 | 心理/投诉数据 |
|---|---|---|
| 访客 | 已公开项目与活动、本次本人提交 | 无权限 |
| 学生 | 本人档案与业务 | 本人工单学生视图；心理仅授权设置，不回显内部标签和风险 |
| 新员工 | 员工公开组织信息、本人日报与有权知识 | 不默认获得敏感权限 |
| 顾问 | 本人客户、负责学生、明确指派事项 | 必须专项授权，并满足对象范围 |
| 班主任 | 当前本班学生及对应业务 | 专项授权后在负责范围内使用 |
| 部门主管 | 实际主管部门，默认不含子部门 | 专项授权与部门范围同时满足 |
| 管理员 | 全域普通业务 | 仍须专项授权，不因 ADMIN 自动开放 |

列表、详情、统计、导出、助手查询和历史报告复用同一规则。归属变化后立即重新判权；历史报告含敏感信息时，还要检查当前授权、学生范围和同意状态，不能只凭生成时权限。

### 3 事务和幂等

一次业务写入、历史追加、站内通知及幂等结果记录在同一事务。外部 AI/ASR 调用前，把需要的数据复制成普通不可变输入并结束数据库事务；外部返回后重新判权，再开启短写事务。

幂等记录以主体、操作和 request_key 定位，保存请求摘要、目标对象和可安全重放的结果。相同键相同内容返回原结果；相同键不同内容返回 409。表单与助手调用同一业务服务，确认令牌不能代替权限。

版本控制使用数据库条件更新或固定主行锁，不接受“先读版本再无条件写入”作为并发保障。创建类竞争以数据库唯一约束和可重放结果兜底；不会把所有唯一冲突都当成成功。

## 六 数据库整合与迁移方案

### 1 唯一事实源

建议以 M5 已迁入的 m5_daily 为正式日报唯一写入源，保留完整审核能力。employee_daily_report 不再接受新增写入，先只读兼容；如果检测到历史数据，逐条映射到正式模型并记录原 ID，不将旧 SUBMITTED 自动伪造为已审核通过。

m5_report 作为报告快照和人工确认文本的保存实体，m5_chat 仅负责授权会话和草稿。可以在此基础上增加审核修订历史、通用幂等记录与后台任务所需的最少支撑结构；具体迁移逐项说明，不能继续声称“数据库永远只有 19 张表”。

M5 当前 UUID 对外保留为不透明字符串，不能强转整数；已有整数业务 ID 继续返回十进制字符串。统一约定“所有 ID 都是字符串”，并按资源说明数值 ID 或 UUID，避免破坏已迁入成果。

### 2 迁移治理

- 引入版本化迁移管理，基础 19 表作为可识别基线，M5 与后续改动形成增量迁移。
- 新库能够一条受控流程完成初始化；已有库先检查结构与版本，不依赖重新挂载初始化 SQL 生效。
- 补齐必要 ORM 字段、唯一键、外键、状态约束和索引，消除 literal_column 及补查字段的临时绕行。
- 日报使用 DATE，时间使用 TIMESTAMPTZ，结构化内容使用有明确 schema_version 的 JSONB；现有字符串数据转换前检查非法值。
- 成绩与日程新增 MANUAL 来源，保留 TEST 标签；生产查询和报告默认排除演示数据，导入来源可追溯。
- 无现存保留数据要求也不执行盲目清库。迁移前自动盘点、生成备份与校验；遇到不能无损转换的内容出具清单。
- 回滚以保留数据为前提。新增业务数据后不盲目 DROP 新表，必要时采用代码回退配合保留新表。

## 七 业务闭环实施设计

### 1 获客到学生

表单/访客草稿/活动报名 → 规范化和查重 → 新增客户或追加跟进 → 项目路由 → 部门池/管理员待分配池 → 顾问认领或分配 → 跟进 → 研判 → 线下签约确认 → 原子创建账号、档案与课程关联 → 通知与学生首次改密。

待分配池提供完整管理入口，不能只有“看见但无法分配”的状态。重复渠道不覆盖已有负责人与销售状态。签约、合同金额、入学日期、实收收入分别表达，不相互冒充。

### 2 客户研判

采用“原文解析 → 字段草稿及证据 → 员工核对 → 按审核规则计算 → 保存报告”。人工确认的事实与模型提取结果分开保存。

画像字段按原资料补齐年龄/生日、当前学历和在读状态、目标项目/国家、语言阶段、留学与就业意愿、经济信息是否充分等。年龄按明确的评估基准日计算；“家里很有钱”等主观表述只保留证据和待核对信息，不自动转换为收入门槛。

新加坡必须按不同培养路径分别建规则，不能把所有项目揉成一个 AND 条件。德国的初步报名条件与后续企业匹配所需语言阶段分开；软性倾向和硬性准入分开。支持经过审核的分支与组合规则、学历同义归一、缺项解释和规则版本，不自行编造评分权重。

Excel 支持工作表选择、表头映射、逐行预览、错误定位和确认后处理；不读取公式外链，不执行宏。文字 PDF/DOCX/TXT 可读文本解析有长度与结构限制；扫描件没有 OCR 时明确拒绝假识别。

### 3 行政审批

学生核对后提交 → 按班主任/顾问/主管路由 → 员工待办及通知 → 审批或转派 → 同事务修改状态/资料 → 学生通知 → 本人查询结果。请假重叠检查在主行锁内完成；只有待审批单可撤销或转派。

调班、换顾问及人员停用通过可执行的交接流程处理，列出未交接记录；交接成功后允许调整关系，不能要求先消灭所有待审业务。

### 4 售后

学生提交 → 部门售后池 → 授权员工认领 → 跟进 → 解决并通知 → 学生确认关闭或重开 → 关闭后评价。主管转派、SLA 起算与重开后的时限口径统一；保留首次响应、首次解决、最近解决、重开次数和最终满意度。

日报与报告只能引用本身有权访问的工单。通知与普通待办不放投诉正文。任何终态之后的动作均经过状态允许表校验。

### 5 心理关怀

有效授权 → 消息直接风险词先行观测与告警 → AI 情绪分析可用时补充观测 → 按业务日期形成日状态 → 风险只按规则升级 → 通知实际负责且有权的人员 → 人工复核、跟进、关闭/驳回。

情绪观测是否有效与告警是否有效分别判断，避免 UNKNOWN 情绪造成直接词告警在周报中消失。撤回后停止新的情绪处理；在途返回重新确认授权。同意重新授予、历史访问及报告撤权策略形成明确规则并覆盖测试。

人工修正必须追加新版本并保留旧证据，由实际主管/管理员及专项授权控制，不覆盖历史。历史日期查询按所选日期计算，不拿当天结果贴上历史日期。

### 6 教务与进度

授权员工录入/导入成绩和日程 → 学生只读查询 → 学生设置或取消提醒 → 正确版本的提醒到时发送并去重。学业评估由后端按成绩制式计算可解释指标，再由 AI 可选整理文字；不同制式和不同满分不能直接混算，缺少成绩返回数据不足。

申请事项保留当前追加事件模型，校验学生范围、阶段顺序、指派人员与序号。完成与结果通知保持原子；界面数据来源明确标注内部登记。外部同步适配器未接通时不声称已实时对接。

### 7 日报与报告

员工草稿 → 提交 → 主管审核通过/退回 → 通过版本进入汇总。主管不得自审，管理员跨部门普通查看与审核能力分别定义。退回/待审接入统一通知和待办。

保留“最近通过内容继续作为有效汇总来源”的原则：员工修改已通过日报时产生待审新修订，报表仍引用旧通过版本，并显示采用的版本和审核时间；新版本通过后才替换。报告生成后的快照不可因后续日报变化而漂移。

## 八 五类报告指标与验收口径

统一采用 Asia/Shanghai 的自然日；周报为周一至周日，本周未结束时注明截至生成日。API 底层时间窗口使用开始包含、结束不包含；上一周期采用同长度窗口，零基数对比返回不可计算并解释，不输出无穷或假百分比。

| 报告 | 必备确定性指标 | 文字分析与限制 |
|---|---|---|
| 客户经营 | 新增、当前意向、签约、流失、转化率定义、渠道/项目/部门维度、周期对比、跟进与转化耗时 | 从事件事实解释路径和流失原因；样本不足不伪造聚类；合同额区分币种且非收入 |
| 日报日汇总 | 审核通过版本数、员工覆盖、应报/已报/未报、分类工作量 | 进展、产出、困难与风险，引用具体通过版本 |
| 日报周汇总 | 周内日覆盖、员工覆盖、去重事项、未完成工作 | 区分多天跟进同一事项与多个新增事项 |
| 心理周报 | 有效观测覆盖、情绪日趋势、风险新增/在办/关闭、直接词信号、跟进时效 | 缺失观测不当作健康；内容按权限与授权状态控制，建议不作为诊断 |
| 投诉周报 | 新增量、期初积压、当前在办、期间解决/关闭、首响与解决耗时、SLA 超时、重开、满意度及样本量、同期对比 | 主题分类来自受控分类或明确标识的 AI 分类；分母与缺失值清楚 |

M5 的 MANAGER_WEEK 可保留为附加模板，但不能替代上述五类。客户历史状态和归属无法从当前字段可靠还原时，先使用已有跟进事件和后续审计事实；无法恢复的历史必须标注不可得，不能倒推造数据。

每个指标包含定义、数值、单位、时间范围、数据来源、计算时间、可用性和限制。预览生成后持久化输入和指标快照，保存/导出引用同一 snapshot_id；正文有人工改写时保留 MANUAL 标记和修订记录。Dify 只组织表达，不修改后端数字。

## 九 Dify 未就绪时的后端交付设计

### 1 六个逻辑能力

| 能力 | 输入范围 | 输出与后端责任 |
|---|---|---|
| VISITOR | 访客消息、公开项目活动摘要、公开知识范围 | 回答、来源、意图和留资/报名草稿 |
| ASSESSMENT | 单客户最少原文、已确认事实、规则版本 | 提取事实、证据和缺项；后端作判定 |
| ENTERPRISE | 员工消息、最少身份能力、受控上下文 | 意图、参数、草稿；后端查询与签发确认卡 |
| STUDENT | 学生消息、授权后由后端选取的本人摘要、情绪观察开关 | 意图、草稿、必要观测；不携带 JWT，不直接写业务 |
| REPORT_ASSISTANT | 本人日报草稿、授权事实摘要、有限会话历史 | 追问与结构化草稿；不直接提交/审核 |
| REPORT_GENERATION | 已核验指标和脱敏事实快照 | 正文、来源引用和限制；数字不由 AI 重算 |

逻辑能力可以映射到独立 Dify 应用，保持各自 key 与配置，不为了统一客户端而共用一把密钥。既有两个 M5 应用保留能力独立性。

### 2 统一契约

继续保留 payload_json / output_json 外层，内部增加明确的 schema_version、request_id、task 与数据版本。输入和输出均以严格类型验证，未知意图、非法枚举、缺字段、过大响应统一处理，不能悄悄变成成功或另一个任务。

运行模式明确为 disabled、mock、live。disabled 不发网络请求；mock 仅测试/演示并标记 MOCK；live 的真实失败返回 UNAVAILABLE/相应错误码，不静默调用样例。访客和学生保留表单路径，报告保留确定性指标与事实，研判规则计算可独立进行但提取缺失必须说明。

配置包括各应用 key、服务地址、连接/读取/总时限、响应长度、允许的协议和模式。同步与流式客户端共享错误分类；只对确定安全的调用重试，包含业务写入的工作流禁止自动重试。任务状态和请求幂等保证前端超时重试不会重复产生业务。

### 3 本轮交付与后续工作流验收分开

本轮交付后端适配器、版本化 JSON Schema、输入输出样例、异常样例、离线测试、导入说明和工作流待接清单。现有 DSL 保留为草稿参考，不能把存在 yml 文件当作已搭建并通过测试。

待用户搭好 Dify 后验证模型、知识库绑定、发布版本、真实鉴权、超时和实际输出，再标记为真实 AI 集成验收完成。在此之前可交付后端和禁用/离线模式，不能宣称完整 AI 线上功能已交付。

## 十 原始资料整理与知识库边界

资料存在以下可直接确认的冲突：企业信息与新人指南的地址不同；德国产品同一资料分别提到不同永居年限；新人指南明确是待填写模板，联系人、系统地址、邮箱等存在重复或不一致；用户信息示例包含不规范手机号及主观家庭经济描述。

拟建立资料清单：来源、文档标识、受众、业务领域、版本、审核状态、有效日期、冲突项和引用位置。公开、员工、学生知识分别管理；内部制度不进入访客知识范围，客户简历、投诉正文和心理观测不进入公共知识库。

费用、录取条件、工作许可和签证政策只能使用已审核版本；本轮不把原资料的政策陈述验证为现行政策。上线前涉及现行政策的审核需要核对官方来源并记录日期。冲突未裁定内容回复资料不足或转人工，不由代码选择一个数字作为事实。

本轮先交付结构化待审核内容与冲突清单。可技术确定的字段映射由开发处理；只能由业务方确认的联系人、价格、承诺、政策来源等单独留待确认，不阻塞其他后端工作。

## 十一 测试环境与验收方案

### 1 环境设计

建议提供独立 PostgreSQL 16 测试 Compose，使用明确包含 test 的专用数据库名和独立卷/端口。测试启动前必须校验目标地址、库名与测试环境标识；仅排除 dify/postgres 等系统库不够。

单元测试无需网络；集成测试使用一次性测试库或独立 schema，数据采用随机隔离标识，不依赖 199% 等真实手机号范围清理。不拿共享开发库、云端库跑删除夹具。对需要 commit 的业务，不用简单嵌套回滚冒充完整隔离。

补齐合成 PDF/DOCX/XLSX/TXT、损坏文件、扫描件和超限文件夹具及可复现生成方式，不把真实简历复制进 Git。补齐 M3、M5 缺失测试。离线 CI 不要求真实 Dify key。

| 编号 | 场景 | 通过标准 |

| 阶段 | 工作 | 阶段出口 |

| S0 基线与环境 | 记录协作成果，建立需求矩阵、独立测试库、运行依赖和迁移基线 | 当前状态可复现，测试绝不触达共享库 |

5. 独立测试环境、合成夹具、单元/数据库/并发/端到端测试及实际验收记录。

## 十三 方案审批时需要关注的决定

用户已经确认后端范围、日报审核口径、管理员普通全域范围和测试环境由本轮设计，不需要重复确认。

建议随本方案批准以下实施方向：

- 正式整合公共文件与 M5，统一入口和权限，保留既有协作代码与必要路径兼容。
- 以 M5 日报为唯一写入源，通过版本可追溯；旧表不再双写，发现历史数据先保留和迁移。
- 为完整后端补齐人工成绩/日程来源、Excel 资料处理和学业评估；通过增量迁移解除仅 TEST 的开发期限制。
- 学生助手改为后端编排与人工确认卡，统一离线/禁用/真实 AI 模式。
- 外部 Dify、ASR、教务系统按独立集成验收交付边界管理；未就绪不假装接通。

资料中的业务承诺、费用、联系人和政策冲突另列待审核项，具体出现时再向用户询问。技术上的常规实现选择在方案确认后自主推进。

本方案确认前仅保留审查产物；确认后才开始 S0 至 S5 的代码实施。后端验收通过与外部 AI 集成通过分别报告，最终状态以实际检查证据为准。
