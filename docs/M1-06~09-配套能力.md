## 二、设计说明

### 2.1 M1-07 为什么 `notify` 不能自己 commit

**问题**：审批请假要同时做两件事：
```
① 改申请状态 → APPROVED
② 通知学生"你的请假通过了"
```

如果 `notify` 内部自己 `commit()`：
```
① 状态改了、已提交
② 发通知时服务器崩了 → 通知没发出去
结果：学生永远不知道自己通过了 —— 闭环断了
```

**所以**：`notify` **接受外部传入的 Session，自己不 commit**，
跟着业务事务一起提交。**要么都成，要么都不成**。

**这也解释了测试里的那条**：
```
✅ test_事务回滚时通知也回滚
   业务失败 → 通知也不该留下
```

### 2.2 M1-07 为什么用 `event_key` 防重复

**问题**：定时任务每分钟扫一次，**同一条提醒会被扫到很多次** →
学生收到 5 条一模一样的"你的考试快到了"。

**所以**：`(recipient_user_id, business_event_key)` **建唯一约束**。
event_key 写成 `schedule:301:reminder:1`，**同一事件再调用会跳过**。

**这样"重复执行"天然安全** —— 不需要额外的去重逻辑。

### 2.3 M1-08 为什么文件名要重新生成

**问题（路径穿越攻击）**：
```
用户上传文件，文件名填 "../../../../etc/passwd"
如果直接用这个名拼路径 → 覆盖了系统文件
```

**所以**：
1. 文件名**重新生成**（`secrets.token_hex(16)`，不用用户给的）
2. **只认扩展名**，且在白名单内
3. 存完后 **`resolve()` 再检查**是否还在存储根目录内（双保险）

**还有"伪造归属"**：文件按 `u/{owner_user_id}/` 分目录，
**owner 来自登录身份，不来自客户端** —— 无法上传到别人的目录。

### 2.4 M1-09 为什么需要单实例锁

**问题**：如果起了两个后端进程（或以后上多副本），
**定时任务会同时跑两遍** → 提醒发两次。

**所以**：用 **PostgreSQL 咨询锁（`pg_try_advisory_lock`）**：

| 好处 | 说明 |
|---|---|
| 不用额外服务 | 不需要 Redis |
| 进程挂了自动解锁 | 锁随连接释放，不会死锁 |
| 非阻塞 | 拿不到锁**直接跳过**，不排队 |

**为什么用数据库锁而不是 Redis**：你们已经跑着 PostgreSQL，
**少一个依赖少一个故障点**。

### 2.5 M1-06 为什么"停用员工"要先检查

**问题**：直接停用一个班主任，他带的班就**没人管了** ——
学生的请假没人批、心理预警没人跟。

**所以**：停用前检查：
- 是否还是班主任 → 要求先交接班级
- 是否还带在读学生 → 要求先交接学生

**这是"防止出现无人负责的数据"**。

## 四、使用方式

### 4.1 发通知（M3/M4 写闭环时用）

```python
from app.core.notification import notify
from app.core.transaction import with_business_transaction

# ⚠️ 在业务事务里调用 —— 通知跟着业务一起提交/回滚
def approve_service(db, service, student_user_id, teacher_id):
    with with_business_transaction(db):
        service.status = "APPROVED"
        service.decided_at = now()
        # 通知学生（同一事务）
        notify(db, f"service:{service.id}:decision:{service.version}",
               recipients=[student_user_id],
               category="SERVICE_DECISION",
               title="您的请假申请已通过",
               related_type="admin_service", related_id=service.id)
    # 事务提交 → 状态和通知一起落库
```

### 4.2 上传文件

```python
from app.core import storage

@app.post("/files")
def upload(file: UploadFile = File(...), user = Depends(require_password_changed)):
    key = storage.save_upload(file, owner_user_id=user.id)
    return ok({"objectKey": key})      # 数据库里存这个 key
```

## 五、注意事项

| ❌ 不要 | 为什么 | ✅ 应该 |
|---|---|---|
| 在 `notify` 里 commit | 业务失败时通知留着 → 数据不一致 | 传外部 Session，跟着事务 |
| 自己写 `db.add(Notification(...))` | 绕过 event_key 去重 → 重复通知 | 用 `notify()` |
| 用用户给的文件名存盘 | **路径穿越漏洞** | 让 `storage.save_upload` 重新生成 |
| 把文件存到静态目录直接暴露 | 谁都能下载别人的简历 | 走鉴权下载接口 |
| 每个实例都开 `SCHEDULER_ENABLED` | 重复发提醒 | 只在一个实例开（有锁兜底但不推荐） |
| 直接停用带学生的顾问 | 学生没人管 | 先交接（`check_can_deactivate`） |
| 主管给自己加权限 | 越权 | 已被拦（测试覆盖） |

### ⚠️ 两条硬规矩

1. **发通知一定要在事务里** —— `notify` **不自己 commit**，
   如果你在事务外调用，`flush` 了但没提交 → 通知其实没落库。

2. **AI 调用绝不能放事务里** —— 顺便再强调（M1-事务管理也说过）：
   Dify 慢，事务期间数据库行被锁着，别人全被堵住。
   **先在事务外调 Dify，再开事务写库 + 发通知。**
