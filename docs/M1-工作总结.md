## 三、架构设计

### 3.1 交付内容

- **`docs/00-架构图.md`**：6 张图（系统总览 / 后端分层 / 请求链路 / 模块划分 / 部署 / 数据流）
- **`docs/00-项目结构说明.md`**：目录结构 + 每层为什么这样分
- **`docs/M1-S4-与规范的对齐.md`**：与规范的差异及理由

### 3.2 整体架构

```
用户（访客/学生/员工/管理层）
   ↓
前端 Vue3+TS（frontend/src）
   │  ⭐ 唯一出口 api/client.ts
   ↓ HTTP /api/v1
后端 FastAPI（backend/app）
   controllers → services → repositories → models
   ＋ core/（横切：认证/权限/事务/通知/文件/调度）
   ↓
PostgreSQL 19 表  ｜  文件存储  ｜  Dify 5 工作流
```

### 3.3 后端八层

| 层 | 职责 |
|---|---|
| `controllers/` | 收请求、鉴权、调 service（**不写业务**） |
| `services/` | 业务规则 + **事务边界** |
| `repositories/` | 查询，**必须带 Scope** |
| `models/` | 表结构 |
| `schemas/` | 接口 DTO（**不直接序列化 ORM**） |
| `core/` | 公共能力（11 个模块） |
| `db/` | 连接池 + Session |
| `jobs/` | 定时任务 |

### 3.4 三个关键架构决策

| 决策 | 为什么 |
|---|---|
| **`controllers` 按「资源」分**（12 个文件） | 一个业务概念一个文件，跨角色共用（如 `feedback.py` 含学生提交+员工处理） |
| **`main.py` 由 M1 一次性注册全部路由** | 避免五个人抢改同一文件 |
| **前端只有 `api/client.ts` 一个出口** | 令牌/错误/request_id 统一处理 |

## 五、公共能力（M1 核心 Interface）

### 5.1 五个核心 Interface

| Interface | 文件 | 作用 |
|---|---|---|
| `get_actor(token)` | `core/deps.py` | 取当前登录人（含令牌失效判断） |
| `build_scope(actor, purpose)` | `core/permissions.py` | **算数据范围**（防越权） |
| `notify(session, event_key, ...)` | `core/notification.py` | 发通知（**不内部 commit**） |
| `verify_confirmation(...)` | `core/confirmation.py` | 确认令牌（AI 提议需用户确认） |
| `with_business_transaction()` | `core/transaction.py` | 事务（多表全成或全败） |

### 5.2 其它公共模块

`config`（配置）、`security`（密码/JWT）、`errors`（异常）、`responses`（统一响应）、
`storage`（文件）、`scheduler`（定时任务）

### 5.3 三个关键约束

| 约束 | 为什么 |
|---|---|
| **范围外返回 404 不是 403** | 403 会泄露"这条数据存在" |
| **通知不自己 commit** | 业务失败时通知要跟着回滚，否则闭环断 |
| **AI 调用放事务外** | Dify 慢，事务会长时间占数据库锁 |

| | 内容 |
