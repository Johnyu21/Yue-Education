## 分工与约束

- Dify 版本固定 1.12.1，DSL 0.5.0。工作流不含 HTTP、数据库或工具调用节点。
- Dify 负责意图识别、保留已有草稿、缺项追问、知识检索、事实提取与文字整理。
- 后端负责登录鉴权、可见范围、真实数据查询、版本与顺序校验、确认凭证、幂等、状态流转、保存及导出。
- 写操作先在悬浮窗展示确认卡，用户确认后调用普通业务接口。知识库不能代替数据库业务记录。
- 留学申请进度查询与请假等行政服务是不同业务。当前学生助手支持档案、成绩、日程、留学申请进度、初始研判查询；行政申请审批结果可在业务页面读取；学生助手已补充ADMIN_SERVICE_PAGE分流提示，不再把请假查询误作留学申请进度。
- 涉及身份字段的资料更正审批仍转业务表单核验；心理与投诉专项内容不混入普通日报。

## 你们以后如何在工作室维护知识库

1. 打开对应应用的编排页面，找到“在工作室选择对应知识库”节点。
2. 客服和学生当前绑定“访客版知识库（对外）”；企业助手保留“内部版知识库（学生与员工）”。学生已移出共用内部库。以后新增学生专用知识库时，只需在学生应用节点切换；不得将学生重新绑定员工专用资料。资料权限不能仅靠提示词保证。
3. 保留已配置的向量模型、检索与重排参数；文档需要索引完成后才能参与检索。
4. 点击“发布→发布更新”。应用不变时，项目 API Key 无需重填。
5. 在项目悬浮窗提问，核对引用文档；资料不足时应明确返回无法核实，不能编造答案。

不需要填写知识库 UUID，不需要在 .env/core config 中预留知识库接口，也不需要你们运行 Python 生成脚本。workflow_config.json 只保存目标版本和开发时的默认模型；知识库绑定由工作室负责。

本轮移除了旧流程中绕过检索的 KNOWLEDGE_ENABLED=False 和写死 DATASET_IDS 的重复开关。知识问答直接进入工作室已配置的检索节点；普通业务草稿直接返回后端，不强制检索知识库。引用只来自该检索节点的实际 metadata，模型只能选择已核验记录编号。

在现有应用中更新 YML：先导出备份，再在画布空白处右键选择“导入 DSL”，选择文件并覆盖草稿，核对模型与知识库后发布。这样保留现有应用与 API Key。导入到另一个工作空间时，必须在新工作室重新选择知识库。

## 本轮实际修改

- 客服、学生、企业三个应用已通过工作室覆盖导入并发布，保留当前模型。学生根据用户确认已改为对外知识库，企业保留内部库；学生越界拒绝与正常问答均已真实验证。
- 报告助手已保留工作室模型并更新发布：员工描述的普通工作可直接整理为工作概述，补充困难/计划时保留已有内容。
- 业务草稿缺少某些必填字段时继续保留已知值，不能因为缺少日期就把整份请假草稿清空。
- 修复后端带助手确认凭证的审批 500：签名载荷函数只接收 decision/note，原调用多传了身份验证参数。
- 报告事实现在包含可见且已审核日报的明日计划；包含不可见专项内容时不转发该日报的自由文本计划。
- 保留多轮草稿、候选消歧、旧确认卡失效、版本和重复提交保护，以及报告快照绑定。
- 生成工具会保留现有 YML 中的工作室模型、依赖和知识库绑定；开发人员重新生成不会清空这些配置。
