## 二、设计说明

### 2.1 为什么 `notify` 不能自己 commit ⭐

**问题**：审批请假要同时做两件事：
```
① 改申请状态 → APPROVED
② 通知学生"你的请假通过了"
```

如果 `notify` 内部自己 `commit()`：
```
① 状态改了、已提交
② 发通知时服务器崩了 → 通知没发出去
结果：学生永远不知道自己通过了 —— 闭环断了
```

**所以**：`notify` **接受外部传入的 Session，自己不 commit**，
跟着业务事务一起提交。**要么都成，要么都不成**。

**验证过**：
```
✅ test_事务回滚时通知也回滚 —— 业务失败 → 通知一条不留
```

### 2.2 为什么用 `event_key` 防重复 ⭐

**问题**：定时任务每分钟扫一次，**同一条提醒会被扫到很多次** →
学生收到 5 条一模一样的"你的考试快到了"。

**所以**：数据库有唯一约束 `(recipient_user_id, business_event_key)`。
event_key 写成 `schedule:301:reminder:1`，**同一事件再调用会跳过**。

**好处**：**"重复执行"天然安全** —— 不需要额外的去重逻辑。

**验证过**：
```
✅ test_同一事件只发一条
```

### 2.3 为什么跳转类型要白名单

**问题**：通知可以带"点击跳转"。如果 `related_type` 任意填，
**可能被用来做钓鱼跳转**（如跳到外部页面）。

**所以**：只允许白名单里的类型（`admin_service`/`feedback_ticket`/...）。

**验证过**：
```
✅ test_通知跳转类型白名单 —— 非法的被忽略
```

### 2.4 为什么"他人不可读"

**问题**：通知是**私人的** —— 学生 A 不该看到学生 B 的通知。

**所以**：`mark_read` 校验 `recipient_user_id == 当前用户`，
不匹配返回 `False`（调用方转成 404）。

**验证过**：
```
✅ test_他人不可读通知
```

## 四、使用方式 ⭐（M3/M4 必看）

### 4.1 发通知 —— 必须在事务里

```python
from app.core.notification import notify
from app.core.transaction import with_business_transaction

def approve_service(db, service, student_user_id):
    """审批请假 —— 状态和通知同一事务"""
    with with_business_transaction(db):
        service.status = "APPROVED"
        service.decided_at = now()

        notify(db, f"service:{service.id}:decision:{service.version}",
               recipients=[student_user_id],
               category="SERVICE_DECISION",
               title="您的请假申请已通过",
               related_type="admin_service", related_id=service.id)
    # 提交 → 状态和通知一起落库；失败 → 一起回滚
```

### 4.2 event_key 怎么起名

**规则**：`<类型>:<主键>:<动作>:<版本或时间戳>`

| 场景 | event_key |
|---|---|
| 请假审批结果 | `service:301:decision:2` |
| 学生提交申请 | `service:302:submit:1` |
| 工单已解决 | `ticket:55:resolved:1` |
| 日程提醒 | `schedule:88:reminder:1` |
| 跟进提醒 | `lead:12:followup:1730000000` |

**关键**：**"同一件事"的 key 必须相同**，这样重复调用不会重复发。

### 4.3 可用的 category

```
SERVICE_DECISION     请假/考务审批结果
SERVICE_SUBMITTED    学生提交申请（推给老师）
FEEDBACK_HANDLING    工单处理进展
FEEDBACK_RESOLVED    工单已解决
FEEDBACK_REOPENED    工单被重新打开
PSYCH_ALERT          心理预警（⚠️ 不含原文）
LEAD_ASSIGNED        线索分配
DAILY_REPORT_RETURN  日报退回
EVENT_OPENED         新活动
SYSTEM               系统
```

### 4.4 查消息 / 标记已读

```python
# 我的消息
items = list_my_notifications(db, user.id, limit=50)

# 标记已读（⚠️ 不是自己的返回 False）
if not mark_read(db, user.id, notification_id):
    raise NotFoundError("消息不存在")     # ⚠️ 404 不是 403
```

## 五、注意事项

| ❌ 不要 | 为什么 | ✅ 应该 |
|---|---|---|
| 在 `notify` 里 commit | 业务失败时通知留着 → 不一致 | 传外部 Session，跟事务走 |
| **在事务外调用 notify** | flush 了但没提交 → **通知其实没落库** | **一定要 `with with_business_transaction`** |
| 自己写 `db.add(Notification(...))` | 绕过 event_key 去重 → 重复通知 | 用 `notify()` |
| event_key 每次生成随机的 | 去重失效 → 重复发 | 用稳定的业务标识 |
| 通知里放心理/投诉原文 | **敏感信息泄露** | 只放摘要和跳转 |
| 他人通知返回 403 | 泄露"这条存在" | 返回 **404** |

### ⚠️ 最容易踩的一条

**在事务外调用 `notify`**：
```python
# ❌ 错：flush 了但没 commit，进程结束就丢了
notify(db, "xxx", [uid], category="SYSTEM", title="x")

# ✅ 对：放进事务
with with_business_transaction(db):
    notify(db, "xxx", [uid], category="SYSTEM", title="x")
```

**也提醒**：**AI 调用（Dify）绝不能放事务里** ——
事务期间数据库行被锁着，Dify 慢会把别人全堵住。
**先在事务外调 Dify，再开事务写库 + 发通知。**
