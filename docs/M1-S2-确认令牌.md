## 二、设计说明

### 2.1 这个"确认令牌"是干什么的

**场景**：学生跟助手说"我要请假 3 天"。

```
❌ 错误做法：AI 直接把请假单写进数据库
   → 学生只是"说了句话"，并没有"批准提交"！AI 理解错就糟了

✅ 正确做法：
   AI 生成"提议卡片"（写着：请假3天、理由：身体不适）
     → 学生看到卡片，点"确认"
     → 才真正提交
```

**确认令牌 = "用户确实点过确认"的证明**。没有它，
**光凭一句话，AI 就替学生提交了申请** —— 这是不能接受的。

### 2.2 为什么令牌要绑定 7 样东西

**问题**：如果令牌里只有"用户a确认过"，会怎样？

```
用户确认了"请假 3 天"     → 拿到令牌
然后用同一个令牌提交"请假 30 天"  → 如果令牌不绑内容，就混过去了 ❌
```

**所以绑死 7 项**（02 文档要求）：

| 绑定项 | 防什么 |
|---|---|
| **actor**（谁） | 拿别人的令牌用不了 |
| **operation**（什么操作） | 拿"确认请假"的令牌去"确认转学生" |
| **entity_id**（哪条记录） | 确认 301 号，却操作 999 号 |
| **payload_hash**（内容指纹） | **确认 A、提交 B**（最关键） |
| **expected_version**（版本） | 确认后别人又改了，你还按旧版提交 |
| **request_key**（幂等键） | 重复提交 |
| **exp**（5 分钟到期） | 令牌被长期持有 |

**任何一项对不上，就拒绝。**

### 2.3 ⚠️ 最重要的一条：令牌不是权限

**M1 文档原话**：

> **提议不是授权，签名也不能替代当前权限和版本检查。**

**意思是**：
```
令牌验证通过 ≠ 你有权限做这件事
```

**为什么**：用户确认的时候可能还有权限，
但**确认之后权限被撤了**（比如被调岗）。如果只看令牌，
就会**拿着"过去的确认"做"现在无权做的事"**。

**所以**：令牌通过后，**调用方必须继续做**：
1. `build_scope` 权限检查（M1-05）
2. 乐观锁版本检查
3. 业务规则检查

**看代码里的注释**：`verify_confirmation` 返回的 claims
**只证明"用户确认过"，不证明"有权限"**。

### 2.4 为什么用独立的 issuer

登录令牌和确认令牌**都用同一个密钥签**。
如果不区分，**登录令牌可能被当成确认令牌用**（或反过来）。

**所以加 `iss: "confirm"`**，校验时也检查它 —— 两种令牌互不通用。

## 四、使用方式

### 4.1 完整流程（学生请假为例）

```python
from app.core.confirmation import sign_confirmation, verify_confirmation, new_request_key

# ---- ① AI 助手生成提议（不写库）----
@router.post("/assistant/messages")
def assistant(msg, user = Depends(require_password_changed)):
    # AI 理解出学生想请假
    service_data = {
        "service_type": "LEAVE", "title": "请假",
        "start_at": "2026-10-20T09:00:00+08:00",
        "end_at": "2026-10-20T17:00:00+08:00",
    }
    rk = new_request_key()
    token = sign_confirmation(user, "SUBMIT_SERVICE",
                              entity_id=None, payload=service_data,
                              expected_version=None, request_key=rk)
    # 返回提议卡片，让用户确认
    return ok({"proposal": {
        "operation": "SUBMIT_SERVICE",
        "preview": service_data,
        "request_key": rk,
        "confirmation_token": token,
        "expires_at": "...5分钟后...",
    }})

# ---- ② 用户点确认 → 调普通业务接口 ----
@router.post("/student-services")
def create_service(req: ServiceCreateRequest,
                   user = Depends(require_password_changed),
                   db: Session = Depends(get_db)):
    # 校验确认令牌
    claims = verify_confirmation(user, req.confirmation_token,
                                 operation="SUBMIT_SERVICE",
                                 entity_id=None,
                                 payload=req.model_dump(include={
                                     "service_type","title","start_at","end_at"}))
    # ⚠️ 到这里只证明"用户确认过"，下面还要查权限！
    scope = build_scope(db, user, "admin_service")
    ...
    with with_business_transaction(db):
        ...
```

### 4.2 关键点：payload 要**逐字段对齐**

**签令牌时用的 payload，必须和校验时用的 payload 完全一致** ——
字段名、字段值、字段顺序（顺序无所谓，我做了排序）。

**建议**：**抽一个函数统一生成 payload**，两处都调它：

```python
def service_payload(req) -> dict:
    return {
        "service_type": req.service_type,
        "title": req.title,
        "start_at": req.start_at.isoformat() if req.start_at else None,
        "end_at": req.end_at.isoformat() if req.end_at else None,
    }
# 生成提议、校验，都用 service_payload(req) → 保证一致
```

## 五、注意事项

| ❌ 不要 | 为什么 | ✅ 应该 |
|---|---|---|
| 令牌通过就直接写库 | **令牌不是权限**，用户可能已被撤权 | 继续做 `build_scope` 权限检查 |
| 令牌通过就跳过版本检查 | 确认后别人可能改过 | 继续做乐观锁检查 |
| 两处 payload 不一致 | 指纹对不上，正常请求也被拒 | 抽一个函数统一生成 payload |
| 拿登录令牌当确认令牌 | 语义不同，会绕过确认环节 | 已用 issuer 隔离，别改 |
| 确认令牌写日志 | **可能被重放** | 日志里**不记令牌原文** |
| 令牌有效期改长 | 越长越容易被重放 | 保持 5 分钟（02 文档要求） |

### ⚠️ 最容易误解的一条

**"校验了令牌" ≠ "校验了权限"。**

很多人以为校验了确认令牌就等于鉴权了 —— **完全不是**。
**令牌只回答"用户确认过吗"，不回答"他能做吗"。**

**所以**：`verify_confirmation` **后面必须跟着** `build_scope`。
这两件事**都要做**，缺一不可。
