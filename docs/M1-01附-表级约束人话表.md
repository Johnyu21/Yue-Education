## 这份表解决什么

`schema.sql` 里有 30 条**表级约束**，长这样：

```sql
CHECK ((fee_amount IS NULL AND fee_currency IS NULL)
       OR (fee_amount IS NOT NULL AND fee_currency IS NOT NULL))
```

**一眼看不懂，但它们全是业务规则**。这份表把它们翻译成人话。

> **为什么写这里，不写进数据库的 `COMMENT`**：
> 数据库注释只有**连库**的人看得到；写这里**全队都能看到**，
> 而且改起来不用动 schema（不违反"冻结后只加不改"）。

**怎么用**：写到相关业务时**回来看一眼**——比如你要做"签约"，就知道
"**签约必须同时写 `signed_at`**"，否则数据库会拒。

---

## 一、必须"同时填"的约束（最容易踩）

这类约束的意思是：**A 和 B 要么都填、要么都不填**，不能只填一个。

| 表 | 约束 | 人话 |
|---|---|---|
| `course_project` | 费用与币种同进同退 | **填了 `fee_amount` 就必须填 `fee_currency`**，反之亦然 |
| `crm_lead` | 合同金额与币种同进同退 | **填了 `contract_amount` 就必须填 `contract_currency`** |
| `notification` | `(related_type IS NULL)=(related_id IS NULL)` | **`related_type` 和 `related_id` 要么都有、要么都没有**——不能只给一半 |

## 二、状态变更必须带"证据"的约束

这类约束的意思是：**状态改成某个值，就必须同时记录"为什么/什么时候"**。

| 表 | 约束 | 人话 |
|---|---|---|
| `crm_lead` | `status <> 'SIGNED' OR signed_at IS NOT NULL` | **改成"已签约"，必须同时填签约时间** `signed_at` |
| `crm_lead` | `status <> 'LOST' OR (lost_at AND loss_reason)` | **改成"已流失"，必须填流失时间 + 流失原因** |
| `employee_daily_report` | `status <> 'SUBMITTED' OR submitted_at IS NOT NULL` | **改成"已提交"，必须填提交时间** |
| `student_feedback_ticket` | `status NOT IN ('RESOLVED','CLOSED') OR (resolved_at AND resolution AND is_notified)` | **改成"已解决/已关闭"，必须同时填：解决时间 + 处理结果 + 已通知学生** |
| `student_feedback_ticket` | `status <> 'CLOSED' OR closed_at IS NOT NULL` | **改成"已关闭"，必须填关闭时间** |
| `student_psych_alert` | `status NOT IN ('DISMISSED','CLOSED') OR (closed_at AND action_note)` | **改成"已驳回/已关闭"，必须填关闭时间 + 处置说明** |

> **背后的道理**：**不允许"无凭据的状态"**——不能出现"已签约但不知道啥时候签的"。
> 写代码时**改状态和填时间要在同一个事务里**。

## 三、时间先后关系的约束

这类约束的意思是：**两个时间点的先后顺序必须合理**。

| 表 | 约束 | 人话 |
|---|---|---|
| `student_admin_service` | 请假时 `end_at > start_at` | **请假的结束时间必须晚于开始时间** |
| `student_academic_schedule` | `end_at >= start_at` | **日程的结束不能早于开始** |
| `student_academic_schedule` | `remind_at <= start_at` | **提醒时间不能晚于日程本身**（提前提醒，不能事后提醒） |
| `student_course_enrollment` | `ended_at >= enrolled_at` | **退出时间不能早于报名时间** |
| `event_lecture` | `end_at > start_at` | **活动结束必须晚于开始** |
| `event_lecture` | `signup_deadline <= start_at` | **报名截止必须在活动开始之前**（不能活动开始了还能报名） |

## 四、类型相关的"必须配套"约束

这类约束的意思是：**选了某个类型，就必须提供配套的字段**。

| 表 | 约束 | 人话 |
|---|---|---|
| `student_admin_service` | `service_type='LEAVE'` 时必须填起止时间 | **选"请假"就必须填开始和结束时间** |
| `student_admin_service` | `service_type='INFO_CHANGE'` 时必须填 `change_request` | **选"信息修改"就必须填改什么**（JSON） |
| `student_score` | `score_type='NUMERIC'` 时必须填数字成绩和满分 | **选"数字"成绩，必须同时给分数和满分**；选"等级/通过制"则不能填数字 |

## 五、身份与授权的约束

| 表 | 约束 | 人话 |
|---|---|---|
| `sys_user` | 学生不能有 role/部门/售后/心理权限 | **学生账号不允许有 `employee_role`、`dept_id`、售后权限、心理权限** |
| | | 员工必须有 role（管理员可无部门） |
| `student_profile` | `psych_consent_status='GRANTED'` 时必须填授权时间和版本 | **"已授权"必须留下"何时授权、哪个版本"**，不能空口说授权了 |
| `sys_department` | `parent_id <> id` | **部门不能把自己当上级**（防树形结构成环） |
| `student_psych_profile` | `emotion_state='UNKNOWN'` 时 `is_valid` 必须为假 | **"未观测"的记录不能标记为有效**（缺失日就是缺失，不造假） |

## 六、组合唯一键的含义（多列 UNIQUE）

这类约束的意思是：**多个字段合起来不能重复**。

| 表 | 约束 | 人话 |
|---|---|---|
| `student_course_enrollment` | `UNIQUE(student_profile_id, course_project_id)` | **同一学生同一课程不能重复报名** |
| `employee_daily_report` | `UNIQUE(employee_user_id, report_date)` | **一个员工一天只能一份日报** |
| `event_registration` | `UNIQUE(event_id, mobile)` | **同一活动、同一手机号只能报一次** |
| `student_psych_profile` | `UNIQUE(student_profile_id, version_no)` | **同一学生画像版本号不能重复** |
| `student_application_progress` | `UNIQUE(case_no, sequence_no)` | **同一申请单内序号不能重复** |
| `notification` | `UNIQUE(recipient_user_id, business_event_key)` | **同一事件对同一人只发一条通知**（防重复推送） |

## 七、复合外键（带 `student_profile_id` 的）

**这是最"绕"的一类**——它保证"**引用的记录属于同一个学生**"，防止跨学生串数据。

| 表 | 约束 | 人话 |
|---|---|---|
| `student_academic_schedule` | `FOREIGN KEY (enrollment_id, student_profile_id)` | **日程关联的课程报名，必须也属于这个学生**——不能给 A 学生挂 B 学生的课 |
| `student_score` | 同上（课程报名 + 考试日程） | **成绩关联的课程/考试，必须属于同一个学生** |
| `student_profile` | `FOREIGN KEY (class_id, dept_id)` | **学生选的班级，必须是本部门的班**——不能跨部门选班 |
| `student_psych_alert` | `FOREIGN KEY (psych_profile_id, student_profile_id)` | **预警关联的画像，必须属于这个学生**——不能给 A 的预警挂 B 的画像 |

> **为什么这么设计**：单列外键只能保证"那条记录存在"，**不能保证"那条记录是同一个学生的"**。
> 加上 `student_profile_id` 一起做外键，就**堵死了"跨学生串联"**。
> ⚠️ **写代码时注意**：**这些表必须带上 `student_profile_id` 一起写**，否则外键对不上。

## 八、其他

| 表 | 约束 | 人话 |
|---|---|---|
| `student_application_progress` | `(sequence_no=1 AND previous_id IS NULL) OR (sequence_no>1 AND previous_id IS NOT NULL)` | **第一条进度没有前驱，之后的每条都必须指向前一条**（形成链条，不能断） |
| `event_registration` | `num_nonnulls(student_profile_id, lead_id)=1` | **报名人要么是学生、要么是线索，且只能有一个**（不能两个都空，也不能两个都填） |
| `event_registration` | `lead_id IS NULL OR cancel_token_hash IS NOT NULL` | **访客（线索）报名，必须给一个取消凭证**（他能自己取消） |
| `student_score` | `data_source='TEST'` | ⚠️ **成绩目前只允许"测试数据"**（本轮不开放成绩录入，见 D02） |

### 两个"部分唯一索引"（只在特定条件下唯一）

这几条**不是普通 UNIQUE**，而是**"只在某些状态下才要求唯一"**：

| 表 | 索引 | 人话 |
|---|---|---|
| `student_psych_alert` | `uq_psych_open_student ... WHERE status IN ('PENDING_REVIEW','CONFIRMED','HANDLING')` | ⚠️ **一个学生同时只能有一个"未关闭"的预警**——已关闭的可以有多个 |
| `crm_lead` | `ix_lead_next_followup ... WHERE status IN ('NEW','FOLLOWING')` | 只为"未结束"的线索建跟进时间索引（加速待办扫描） |

> **`student_psych_alert` 那条很关键**：它保证**同一个学生不会挂着两条待处理预警**。
> 写代码时**要么复现已有预警（`repeat_count+1`），要么先关掉旧的**，不能直接插第二条。

---

## 写代码时的三条纪律

1. **"改状态 + 填时间"必须在同一事务**——否则数据库直接拒。
2. **带 `student_profile_id` 的复合外键表**，写的时候**一定要带这个字段**。
3. **遇到"数据库报约束错误"**，回来查这张表——**它是业务规则，不是 bug**。

## 附：约束与人话对照速查

| 约束形态 | 一眼看懂的意思 |
|---|---|
| `A IS NULL AND B IS NULL) OR (A IS NOT NULL AND B IS NOT NULL)` | **A、B 同进同退** |
| `status <> 'X' OR 某字段 IS NOT NULL` | **改成 X 就必须填那个字段** |
| `end > start` | **后者必须晚于前者** |
| `type='X' OR 某字段 IS NOT NULL` | **选了 X 类型就必须配套填** |
| `num_nonnulls(a,b)=1` | **a、b 恰好填一个** |
| `(a IS NULL)=(b IS NULL)` | **a、b 要么都有、要么都没有** |
| `UNIQUE(a, b)` | **a+b 组合不能重复** |
| `FOREIGN KEY (x, student_profile_id)` | **x 必须属于同一学生** |
