## 三、设计说明

### 3.1 为什么顶层分三大块

```
backend/    代码——要跑起来的东西
deploy/     部署——把代码跑起来所需要的（数据库、环境）
docs/       文档——给人看的东西
```

**问题**：如果全堆在一起（像一开始那样），会出现：
- 新人不知道哪个是代码、哪个是配置
- `git` 提交时容易把 `.env`（密码）也传上去

**分三块的好处**：
- **一眼知道该往哪放**：写代码 → `backend/`；改数据库 → `deploy/`；写说明 → `docs/`
- **权限边界清晰**：`deploy/` 只有 P1 动；`docs/` 大家都能改
- **打包/部署时目标明确**：只把 `backend/` + `deploy/` 部署，`docs/` 不用上服务器

### 3.2 为什么 `backend/app/` 要分七层

**问题**：如果所有代码堆在几个文件里，会出现：
- 改一个功能要翻遍整个项目
- 两个人改同一个文件频繁冲突
- "这个逻辑该放哪"反复争论

**分层的判断标准**：**新功能该写进哪个文件夹，一目了然**。

| 层 | 一句话 | 举例 |
|---|---|---|
| `core/` | **公共能力**，跟业务无关 | 怎么返回错误、怎么鉴权 |
| `db/` | 数据库连接 | 怎么连库 |
| `models/` | **表长什么样**（对数据库） | `sys_user` 表有哪些列 |
| `schemas/` | **接口传什么**（对前端） | 登录请求要什么字段 |
| `services/` | **业务规则 + 事务** | "转学生"要同时建 5 样东西 |
| `controllers/` | **路由**（URL → 函数） | `POST /login` 调哪个函数 |
| `integrations/` | **外部系统** | 怎么调 Dify |

### 3.3 ⚠️ 最容易混的：`models` vs `schemas`

**这两个必须分清**，是本项目出现最多混淆的地方：

| | `models/` | `schemas/` |
|---|---|---|
| 对应什么 | **数据库表** | **接口数据** |
| 一句话 | 数据库怎么**存** | 接口怎么**传** |
| 谁用 | SQLAlchemy | Pydantic |
| 例子 | `class SysUser(Base)` 对应 `sys_user` 表 | `class LoginIn` 对应登录请求体 |

**记忆法**：**Model 对数据库，Schema 对接口**。一个进库，一个上线。

### 3.4 为什么 `core/` 单独拎出来

**问题**：`core/` 里的东西是**全组共用的**（错误码、响应格式、权限检查）。
如果这些分散在各模块，会出现：
- 张三写一套错误格式、李四写另一套
- 改一处要通知所有人

**所以集中放 `core/`，并在本文档里说明"公共文件不要自己改"**（要改先跟 P1 说）。

### 3.5 为什么 `docs/` 不放 `backend/` 里

**问题**：文档和代码混在一起时，**改代码的人不一定会看文档，看文档的人不知道代码在哪**。

**分开放的好处**：
- 文档给**人**看（尤其甲方、评审）
- 代码给**机器 + 开发者**看
- 打包部署时**文档不用上服务器**

### 3.6 为什么 `deploy/` 要独立

**问题**：数据库脚本（`schema.sql`）和 `docker-compose.yml`
**既不是"代码"也不是"文档"**，是**部署物料**。

**独立的意义**：
- 部署时**只需要 `deploy/` + `backend/`**
- 云上同学只用 `docker-compose.云端.yml` + `schema.sql`，**不用给他整个仓库**
- 数据相关的改动**都在这一处**，不会散落

### 3.7 ⚠️ 为什么 `controllers/` 按"人"分文件

**问题**：五个人都要加接口。如果按"资源"分（如 `leads.py` 里既有 M2 的留资、
又有 M3 的跟进），**两个人会同时改一个文件** → 频繁冲突。

**所以按"负责模块"分**：

| 文件 | 负责人 | 装什么 |
|---|---|---|
| `auth.py` | M1 | 登录、改密 |
| `organization.py` | M1 | 部门/班级/账号/通知/文件 |
| `public.py` | M2 | 访客、活动、研判 |
| `employee.py` | M3 | CRM、转学生、日报 |
| `student.py` | M4 | 请假、工单、心理、教务 |
| `reports.py` | M5 | 报告 |

**一人一个文件 → 谁也不会改到别人的**。

### 3.8 ⚠️ 为什么 `main.py` 由 M1 一次性注册好

**问题**：每人加接口都要在 `main.py` 注册路由：
```python
app.include_router(auth_router.router)      # M1
app.include_router(public_router.router)    # M2
app.include_router(employee_router.router)  # M3   ← 三个人改同一个文件
```

**所以**：**M1 把六个路由全部注册好**，别人**只填自己 `controllers/` 里的文件**，
**不用碰 `main.py`** → 彻底避免抢文件。

**已搭好空壳**：每个 `controllers/xxx.py` 里已有全部接口的**占位函数**
（返回 `501 NOT_IMPLEMENTED` + 负责人），**你只需把 `_todo()` 换成真实实现**。

## 四、使用方式

### 4.1 新人第一天：按这个顺序认路

```
1. 看 README.md              → 知道项目是干嘛的
2. 看 docs/                  → 知道有哪些模块、怎么协作
3. 看 docs/00-AI编码提示词模板.md → ⭐ 写代码前必看
4. 看 backend/app/core/      → 知道公共能力有哪些（别重复造）
5. 看 backend/app/controllers/auth.py → 一个完整接口长什么样
```

### 4.2 想加一个功能，文件放哪

| 你要做的事 | 放哪 |
|---|---|
| 加一张表 | `deploy/schema.sql` + `backend/app/models/` |
| 加一个接口 | `controllers/` + `schemas/` |
| 写业务规则 | `services/` |
| 改错误码 / 响应格式 | `core/errors.py` / `core/responses.py`（⚠️ 先问 P1） |
| 接 Dify | `integrations/` |
| 写测试 | `backend/tests/` |
| 写说明 | `docs/` |

### 4.3 本地启动（三步）

```bash
# ① 起数据库
cd deploy && docker compose up -d

# ② 配后端
cd ../backend
cp .env.example .env          # 按需改

# ③ 装依赖 + 启动
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

### 4.4 云上部署

```bash
# 只需要 deploy/ 里的两个文件
scp deploy/docker-compose.云端.yml deploy/schema.sql deploy/env.example 服务器:/opt/edu/
# 服务器上：cp env.example .env && docker compose -f docker-compose.云端.yml up -d
```

## 五、注意事项

| ❌ 不要 | 为什么 | ✅ 应该 |
|---|---|---|
| 把 `.env` 提交到 git | **含密码**，传上去就泄露了 | 已在 `.gitignore` 排除；只传 `.env.example` |
| 把 `.venv/` 提交到 git | **98MB**，而且每人重建就行 | 已在 `.gitignore` 排除 |
| 改 `core/` 里的文件不问人 | 全组共用，改一处影响所有人 | 先跟 P1 说，改完通知全组 |
| 把文档放 `backend/` 里 | 部署时会被带上服务器，浪费 | 放 `docs/` |
| 把表结构改在别处 | 会和其他地方不一致 | 只改 `deploy/schema.sql` |
| 复制公共能力到自己模块 | 会出现两套，改起来不同步 | 用 `from app.core.xxx import` |
| 在 `controllers/` 里写业务逻辑 | 路由层该薄，业务在 services | 逻辑写 `services/` |

### ⚠️ 两条硬规矩

1. **`.env` / `.venv` / `logs/` / `uploads/` 绝不提交** ——
   已在 `.gitignore` **第 5、11、22、26 行**排除。**提交前用 `git status` 看一眼**。

2. **公共文件（`core/`、`deploy/schema.sql`）变更要先说** ——
   它们是全组的"地基"，一个人改了所有人受影响。
